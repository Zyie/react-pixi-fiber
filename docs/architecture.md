# Architecture

react-pixi-fiber renders react-three-fiber (r3f) v10 with pixi-3d, and pixi.js 2D in the same tree. r3f's core runs as a fork that asks the renderer support where it used to reach into three.js objects (the renderer hooks); pixi-3d and pixi.js 2D plug into it as one renderer support, and a thin layer gives pixi-3d the three.js surface that r3f apps reach for. The goal is that an r3f app only swaps its import, and that 2D is written the same way.

`docs/feasibility.md` has the findings this design rests on. `CODING_STANDARDS.md` says how the code is written.

```
src/index.tsx           react-pixi-fiber: r3f's API, typed against pixi-3d
src/three.ts            react-pixi-fiber/three: three's API (math, classes, constants) over pixi-3d
src/addons/index.ts     react-pixi-fiber/addons: what r3f apps import from three/addons
  src/root/             createRoot and <Canvas>, bound to the pixi provider
  src/support/          pixi-3d as an r3f renderer support (kind 'pixi')
  src/renderer/         PixiRenderer: three's renderer surface over pixi.js and View3Ds
  src/catalog/          the namespace JSX names resolve in, built from the area modules below
    objects/ scene/ lights/ geometries/ materials/ drawables/ instancing/ textures/
                        classes under three's names (<mesh>, <boxGeometry>, ...), one module per area
    constants.ts        three's constants
  src/math/             three's math: Vector3, Euler, Quaternion, Matrix4, Color, ...
  src/events/           the Raycaster's area module, and r3f's pointer events with onDoubleClick fixed
  src/loaders/          three's core loaders and useTextures
  src/animation/        three's AnimationMixer, clips, tracks and EventDispatcher
  src/environment/      render targets, CubeCamera, Controls, <Environment> and its hooks, EnvironmentMaps
  src/addons/           loaders/ controls/ environment/: GLTFLoader, OrbitControls, HDRLoader, ...
  src/two-d/            pixi.js 2D: the 2D elements, their r3f surface, the screen layer, 2D hit testing, AssetsLoader,
                        and the bridges to 3D: Anchor2D, and View3D, Layer3D and RenderTexture2D in bridges/
  src/compat/           three's members on pixi-3d's prototypes: Object3D, materials, raycasting
  src/types/            RootState, ThreeElements, events, props: our types, naming pixi-3d
  src/r3f/              r3f's packages/fiber, forked: core calls the renderer hooks (src/r3f/README.md)
```

## The forked core

`src/r3f` is `packages/fiber` of react-three-fiber (`src`, `types` and `package.json`) at the commit `scripts/repos/manifest.mts` pins, which `.repos/react-three-fiber` is checked out at. Its core asks the root's renderer support where it used to reach into three.js objects. `src/r3f/README.md`, written for r3f's maintainers, gives the interface, each hook, what core did before and why. The whole change is `src/r3f/fork.diff`: `npm run diff:r3f` writes it, `scripts/r3f/fork.mts --check` fails when it is stale and runs in `npm run test:lint`, and `git apply` takes it in an upstream checkout. r3f's own test suite passes on the fork as on upstream.

Besides the diff, the fork holds files of ours, listed in the script's `EXTRAS`:

- `react-reconciler/{index,constants}.{js,d.ts}`, at the relative path core imports. Upstream generates an ESM build of react-reconciler there at install time; ours re-exports the npm package, naming each constant, because `export *` from its CommonJS `constants` module loses exports under Vite.
- `README.md` (its diff size line is the script's) and `fork.diff`.

Core never imports `three` for a value. It reaches the renderer through these seams, and each is ours to fill:

- The renderer hooks (`RendererHooks` in `types/provider.d.ts`): `add` and `remove` for every tree change, `isInteractive` for which objects are nodes, `defaultAttach`, `hitTest` and `compareHits` in the event pipeline, and `dispose`.
- `getThree()` (`core/three.ts`): `support.three` of the first root. Core builds its own objects from it: `Raycaster`, `Vector2`, `Vector3`, `Scene`, `PerspectiveCamera`, `Frustum`, and reads a few constants.
- `resolveConstructor()` (`core/extend.ts`): an element name resolves through `extend()` registrations, then `support.catalog` of the root's renderer.
- Duck typing that is left: `uuid`, `traverseAncestors`, `parent`, `visible`, `userData`, `raycast !== null`, and the members core calls on its own camera, raycaster and frustum. Core never uses `instanceof`.

We use core's modules (root, reconciler, store, loop, events, portal, hooks) through `src/index.tsx`. We don't use `core/components/Environment`, `core/hooks/useEnvironment` (three's addons) or `core/hooks/useRenderTarget` (it never disposes its target); `src/environment` has adapted copies of all three. Nor do we use r3f's entries (`index.tsx`, `legacy.tsx`, `webgpu/`), `web/Canvas.tsx` (it imports Environment; `src/root/Canvas.tsx` is its adapted copy) or `support/*` (three's renderers, with three's hooks in `support/threeHooks.ts`). They stay in the fork as upstream has them, but for the hooks. `legacy.tsx` and `support/webgl.ts` matter: the parity harness renders scenes through them.

## The support

`src/support/pixiSupport.ts` is the object r3f's core loads when a root is configured, with the same shape as r3f's `support/webgpu.ts`:

| Field                              | Value                                                                                                                                                                                              |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kind`                             | `'pixi'`. Core's only branch on it tests for `'webgl'` (`core/renderer.ts`), so a pixi root takes the path that awaits the renderer's async `init()`, and the WebGL-only occlusion gate stays off. |
| `three`, `catalog`                 | The catalog (below), for both: core builds its default raycaster, camera and scene from it, and element names resolve in it.                                                                       |
| `Renderer`                         | `PixiRenderer`.                                                                                                                                                                                    |
| `RenderTarget`, `CubeRenderTarget` | `WebGLRenderTarget` and `WebGLCubeRenderTarget` (`src/environment`), which `useRenderTarget` and `<Environment>` make.                                                                             |
| `CanvasTarget`, `occlusion`        | Not available: pixi.js can't share a renderer between canvases, and pixi-3d has no occlusion queries.                                                                                              |
| The hooks                          | `pixiHooks` (`src/support/hooks.ts`), below.                                                                                                                                                       |

The hooks are where core meets pixi's objects, over what the compat layer and the 2D surface give pixi's classes:

- `add(parent, child, before)`: a 3D node goes into a 3D node's children, through `addChildAt` before a sibling; a 2D object under a 3D node goes through `addToScene` (the scene's screen layer, or an anchor); anything under a 2D container through `add2D` (`src/two-d/surface.ts`), where its element is among its siblings. `remove` mirrors it with `removeFromScene` and `remove2D`.
- `isInteractive`: a `Container3D`, a pixi.js `Container` or a `Particle`. `defaultAttach`: `'geometry'` for a `Geometry3D`, `'material'` for a `BaseMaterial3D`.
- `hitTest`: a 2D element hit tests its screen layer (`hitTestScreen`, "pixi.js 2D" below); a 3D node casts the raycaster of its root or portal.
- `compareHits`: draw order (`src/events/hitOrder.ts`). Each hit carries where it is drawn: pairs of a band (2D over the 3D, the 3D, 2D under it) and a place in it (a 2D object's place from the front, a 3D hit's distance), the outermost layer first. A portal drawn inside another layer starts with the order of what holds it, and a hit inside a layer sorts before the hit of what holds it, as a child's event comes before its parent's. `distance` stays the ray's.
- `dispose`: the object's own `dispose`, which the compat layer and the 2D surface give pixi's classes; a `Scene` is never freed.

`src/support/provider.ts` offers it in the provider's `webgpu` slot, the one whose path awaits `init()`. The loader, `loadPixiSupport()`, first runs `installObject3DSurface()`, so the prototype patches happen when the first root configures and never on import.

`src/root/createRoot.ts` wraps core's `createRoot(canvas, provider)`. Its `configure` reads `gl` as `renderer`, so code written for `@react-three/fiber/legacy` runs, and forces `share: false`: pixi.js can't draw one renderer into several canvases, so every canvas gets its own and `primary` is ignored.

`src/root/Canvas.tsx` is r3f's `web/Canvas.tsx`, adapted: same measuring, Suspense blocking, error boundary, event wiring and teardown, without three's `<Environment>`. `background` takes a colour, which it puts on `scene.background`.

## The compat layer

`src/compat/installObject3DSurface.ts` patches pixi-3d's prototypes once, so every node answers core's duck-typed checks and three's API, including nodes pixi-3d builds itself (glTF nodes passed to `<primitive>`):

- `Container3D` gets three's `Object3D` surface (`Object3DMembers`): `isObject3D`, `id` and `uuid` (from `uid`), `name` (over `label`), `type`, `userData`, `up`, `add`, `remove`, `clear`, `attach` (pixi-3d's `reparentChild`), `traverse`, `traverseVisible`, `traverseAncestors`, `getObjectByName`, `getObjectById`, `getObjectByProperty`, `getWorldPosition`, `getWorldQuaternion`, `getWorldScale`, `getWorldDirection`, `localToWorld`, `worldToLocal`, `rotateX`/`Y`/`Z`/`OnAxis`/`OnWorldAxis`, `translateX`/`Y`/`Z`/`OnAxis`, `applyMatrix4`, `applyQuaternion`, the `setRotationFrom*` methods, `lookAt(x, y, z)` (keeping `up`; cameras and lights face it with -Z, as pixi-3d's do), `raycast` (a no-op) and `dispose` (`destroy`). `renderOrder` and `frustumCulled` are kept and inert.
- `rotation` is replaced with an `Euler` (`src/math/Euler.ts`) per node, made on first read from the quaternion. Writing it writes the quaternion through its order; any change to the quaternion (`set`, `slerp`, `lookAt`, an animation) writes the angles back, through a wrapper on `Container3D._onUpdate`, the callback a node's vectors call when they change. pixi-3d's own XYZ `rotation` is never written. `angle` is a degree view over the same `Euler`.
- `matrix` is pixi-3d's `localTransform`, built from the components when read. `matrixAutoUpdate = false` gives the node an own `updateLocalTransform` that does nothing, so the transform pass keeps the matrix as set; reading `matrix` marks the node's transform changed (`_onUpdate()`), so an edit through it shows next frame. `updateMatrix` builds it from the components on demand. `matrixWorld` is worked out when read; `updateMatrixWorld` and `updateWorldMatrix` are no-ops.
- `ObservableVector3` (a node's `position` and `scale`), `ObservableQuaternion` and pixi-3d's `Matrix4` get the members three's classes have and pixi-3d's lack, copied from the classes in `src/math` (the `*_MEMBERS` lists beside them), and typed by the interfaces in `src/compat/threeMembers.ts`. `ObservableQuaternion.setFromEuler` reads an Euler's order. The matrix members that take other arguments in three (`setPosition(x, y, z)`, `makeTranslation(vector)`, `toArray(array, offset)`) fall back to pixi-3d's for pixi-3d's arguments.
- `Mesh3D.raycast`: three's `Mesh.raycast`, ported over the geometry's attributes, installed by `installRaycasting` in `src/compat/Raycaster.ts`.
- `BaseMaterial3D`'s `_deriveLayoutFromBits`, `_setTextureSlot` and `destroy` are wrapped by `installTextureTracking` (`src/catalog/textures/textureTransform.ts`), so each three `Texture` knows the materials that hold it. A change to its `offset`, `repeat`, `rotation`, `center` or `flipY` rewrites the material's `uvTransform`, pixi-3d's one UV transform per material, from the material's `map` (or its first three texture). `flipY` folds in there: the catalog's geometries give three's UVs upside down, which a flipped image matches, so a texture with `flipY` off, such as a `DataTexture`, gets a flip; a glTF texture, on glTF's own UVs, gets one only with `flipY` on.
- `Camera3D`: `isCamera`, `isPerspectiveCamera`, `isOrthographicCamera`, `type`, a `getWorldDirection` along -Z, and `projectionMatrix`, `projectionMatrixInverse`, `matrixWorldInverse` worked out when read (`cameraMatrices.ts`). pixi-3d fills `camera.projection` and `camera.view` only while drawing, so they're a frame old between frames and identity before the first one.
- `Mesh3D`, `Sprite3D`, `Model3D` and `Light` get three's `is*` flags and `type`; pixi-3d's lights keep their own `type`, which their shaders read.
- `Geometry3D.isBufferGeometry`, `BaseMaterial3D.isMaterial`, three's flags, and `dispose` on both, which the `dispose` hook calls when an element unmounts.
- `BaseMaterial3D` gets three's `Material` fields (`MaterialMembers`, `installMaterialSurface` in `src/compat/materialSurface.ts`): `side`, `transparent`, `opacity`, `alphaTest`, `depthTest`, `depthWrite`, `blending`, `visible`, `polygonOffset`, `toneMapped` (pixi-3d's `_skipsToneCurve`, inverted, which ends the shader with pixi-3d's sRGB encode alone) and `needsUpdate` drive pixi-3d's state and shader at any time, for a glTF model's materials too. Each change rebuilds the meshes' shaders and asks every view drawing the material to record its draws again, since pixi-3d's default passes keep replaying recorded draws. three code often builds materials at module scope, so the first catalog material installs the surface too, if no root has yet.
- `Mesh3D.defaultOptions` gets a placeholder geometry and material, because core constructs `<mesh3D>` with no arguments and attaches them afterwards. The placeholder geometry is a zero-size box, which draws and picks nothing, like three's empty `BufferGeometry`.

The patches are typed: `PixiMixins.Container3D` and the `@pixi/3d` module are augmented with `Object3DMembers`, `CameraMembers` and the `Three*Members` interfaces. A type can't narrow what pixi-3d's classes declare, so the catalog's node classes re-declare `rotation` as an `Euler` and `lookAt` with three's arguments (`lookAtPoint`); on pixi-3d's own classes the types stay pixi-3d's and the values are the same.

The patches reach a few of pixi-3d's internals: `_onUpdate` (to mark a node changed and to follow its quaternion), `_localTransformDirty` and `rotationDirty`. Each is a candidate for a public pixi-3d API (`docs/feasibility.md`, section 6).

The `Raycaster` (`src/compat/Raycaster.ts`) builds its ray from the camera's own matrices (any camera picks, not only one a view draws with), walks objects through their `raycast` method as three does, and returns three's intersection shape: `distance`, `point`, `object`, `face` (`a`, `b`, `c`, `normal`), `faceIndex`, `barycoord`, `uv`, `normal`, `instanceId`. A mesh's `raycast` is three r187's `Mesh.raycast`: a bounding sphere and box test, then three's watertight triangle test on every triangle, read through the position attribute's stride and offset, so every triangle the ray crosses is a hit. The loop runs in `crossTriangles` over typed arrays and numbers, so it allocates nothing per triangle. As in three, hidden objects are hit, and the material's `side` (or pixi-3d's `doubleSided`) decides which faces count. A `BufferGeometry` hands pixi-3d `1 - v`, so its hits report `uv` turned back. `Points`, `Line`, `LineSegments`, `LineLoop` and `Sprite` have `raycast` methods of their own (`src/catalog/drawables/raycastDrawables.ts`), three's, with `raycaster.params` thresholds and `index` and `distanceToRay` on their hits; the event layer reaches them as it reaches meshes. There are no `layers`.

`src/events/pointerEvents.ts` is the event layer `<Canvas>` and the `events` export use: core's `createPointerEvents`, with `onDoubleClick` given the last pointerdown's `pointerId`, since r3f v10 keys pointerdown hits by it and Chrome's `dblclick` has none. It isn't in the `src/events` area module, so it stays out of the catalog and `react-pixi-fiber/three`.

`InstancedMesh` (`src/catalog/instancing`) extends pixi-3d's `BatchedMesh3D`, one slot per instance. `setMatrixAt` and `setColorAt` write the slot and three's arrays; `needsUpdate` copies the arrays after direct writes. Instance colours live in the batch's instance data, and a material can only read instance data through a shader bit fixed when it is built, so the slots draw with a twin of the material (`instanceColorMaterial.ts`): the same class with the colour bit in front of its bits, kept in step through the material's `update` and `_setTextureSlot`, and freed with the last mesh that uses it.

## The math

`src/math` has three's math classes, which `react-pixi-fiber/three` exports and the catalog registers under the names core builds by (`Vector3`, `Frustum`, ...). Each extends pixi-3d's class of the same kind (`Vector3`, `Quaternion`, `Matrix4`, `Box` as `Box3`, `Sphere`, `Ray`, `Plane`, `Spherical`, `Frustum`) and adds what three has and pixi-3d lacks, so pixi-3d takes them wherever it takes its own; pixi-3d's methods already take three's arguments, with an optional `out` last. `Euler` extends `ObservableVector3`, so a node's `rotation` can be one. `Color` is three's, with three's colour management (`ColorManagement`): channels in linear sRGB, CSS colours and hex numbers read as sRGB. `toPixiColor` hands a `Color` to pixi-3d as the display `ColorSource` pixi-3d decodes back to the same linear values, encoded with pixi-3d's own `linearToSrgb`; `toDisplayColor` encodes it to sRGB as three outputs it, for what pixi.js draws without decoding, such as a clear colour or a 2D tint. `MathUtils` and `Clock` are three's.

## The catalog

`src/catalog/catalog.ts` builds the namespace core reads as `getThree()` and resolves element names in: pixi-3d's exports, then the three-named classes of every area module, then three's constants.

- pixi-3d's own names stay reachable: `<mesh3D>`, `<cubeGeometry>`, `<material3D>`, `<flatMaterial>`, with pixi-3d's options-object constructors.
- Three-named aliases win over pixi-3d classes of the same name (`SphereGeometry`, `AmbientLight`, `DirectionalLight`, `PointLight`, `PlaneGeometry`, `Vector3`, ...), whose options-object constructors would ignore three's positional `args`. Each alias extends the pixi-3d class, takes three's constructor and defaults, and renames fields (`color` over `baseColor`, `metalness` over `metallic`, `opacity` over `alpha`, `transparent` over `alphaMode`).
- A material's `color` and `emissive` are three `Color`s that write pixi-3d's `baseColor` and emissive colour on every change. `MeshStandardMaterial` is built with pixi-3d's emissive feature on, black until set, since pixi-3d can't turn it on later.
- Every geometry is a `BufferGeometry` (`src/catalog/geometries`), a `Geometry3D` built by three's own generator. It keeps three's attributes beside pixi-3d's: `attributes` is a proxy that reads and writes three's names and iterates pixi-3d's. `position`, `normal`, `uv` (as `1 - v`, since three flips images on load), `color` and `tangent` are drawn. A change packs the geometry into pixi-3d's shared buffers again, or, under `DynamicDrawUsage`, it draws from its own. Points and lines set its draw mode: a camera-facing quad per point, or vertex pairs as lines.
- The standard and physical materials swap pixi-3d's PBR material and lighting bits for three's (`threeStandardBits.ts`) in `getPrimaryDescriptor`; each catalog material also adds a normal flip for `BackSide` (`threeDescriptor`) and works in linear light (`colorSpace: 'linear'`), where pixi-3d's `FlatMaterial` works on colours as authored. `MeshNormalMaterial` takes pixi-3d's display path instead, which leaves its colour unencoded, as three's. `MeshPhysicalMaterial` lays pixi-3d's features out again when one is first set before the first draw.
- `DirectionalLight` starts one unit up and shines at its `target`, as three's does; the renderer turns it toward the target before each frame, since pixi-3d's light shines along its local -Z.
- `PerspectiveCamera` and `OrthographicCamera` override pixi-3d's `computeProjection` with three's projection, built from the settings `updateProjectionMatrix` last saw (core calls it on every resize): a camera's own `aspect`, `zoom`, film offset, view offset and off-centre orthographic bounds. Lights carry three's `LightShadow` classes and three `Color`s.

The classes live in area modules, each a folder with an `index.ts` that exports its classes by name. `catalog.ts` spreads every area module into the namespace, and `src/three.ts` re-exports each with `export *`, so a class an area module exports is in the catalog, has a JSX element and is exported from `react-pixi-fiber/three` at once:

| Area module                                                                | Holds                                                                                                                                          |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/math`                                                                 | three's math                                                                                                                                   |
| `src/catalog/objects`                                                      | `Object3D`, `Group`, `Mesh`, `SkinnedMesh`, `Skeleton`, `Bone`                                                                                 |
| `src/catalog/scene`                                                        | `Scene` and the cameras; fog and backgrounds                                                                                                   |
| `src/catalog/lights`                                                       | lights and their shadows                                                                                                                       |
| `src/catalog/geometries`, `src/catalog/materials`, `src/catalog/drawables` | geometries and `BufferGeometry`, materials; lines, points, sprites and helpers                                                                 |
| `src/catalog/instancing`                                                   | `InstancedMesh`, `InstancedBufferAttribute`                                                                                                    |
| `src/catalog/textures`, `src/loaders`, `src/animation`                     | `Texture` and its kinds; three's core loaders; `AnimationMixer`, clips, tracks and `EventDispatcher`                                           |
| `src/events`                                                               | the `Raycaster` (from `src/compat/Raycaster.ts`)                                                                                               |
| `src/environment`                                                          | render targets, `CubeCamera` and `Controls`; the `<Environment>` components and the hooks live beside it and are exported from `src/index.tsx` |
| `src/addons/loaders`, `src/addons/controls`, `src/addons/environment`      | `react-pixi-fiber/addons` only: `GLTFLoader`, `DRACOLoader`, `MeshoptDecoder`, `OrbitControls`, `MapControls`, `HDRLoader`, `RGBELoader`       |
| `src/two-d`                                                                | pixi.js's 2D classes under their element names (`Sprite2D`, ...); in the catalog only, not in `react-pixi-fiber/three` (see "pixi.js 2D")      |

`ThreeElements` in `src/index.tsx` is the JSX element map over the catalog's type, and augments React's `JSX.IntrinsicElements`. A catalog class whose name HTML already uses is reachable with a `three` prefix: pixi-3d's `Track` is `<threeTrack>`.

### Adding to the catalog

1. **The class.** Write it in its own file in its area's folder (`src/catalog/lights/SpotLight.ts`), under three's name, with three's constructor and defaults, extending the pixi-3d class it maps to. Its JSDoc says what differs from three. A node class (one that extends a pixi-3d `Container3D`) re-declares `rotation` as an `Euler` and `lookAt` with three's arguments, as `src/catalog/objects/Mesh.ts` does. Colour fields are three `Color`s handed to pixi-3d with `toPixiColor`, as `src/catalog/materials/MeshStandardMaterial.ts` does.
2. **Its export.** Add one line to the area's `index.ts`: `export { SpotLight } from './SpotLight';`. That puts it in the catalog, gives it an element (`<spotLight>`) typed from its class, and exports it from `react-pixi-fiber/three`. Nothing else is shared: `catalog.ts`, `src/three.ts` and `src/index.tsx` don't change. A class for `react-pixi-fiber/addons` goes in `src/addons/loaders`, `src/addons/controls` or `src/addons/environment` the same way. Two areas never export the same name: `src/three.ts` would see a duplicate `export *`.
3. **Its three counterpart.** A scene that uses the element or imports the class from `react-pixi-fiber/three` renders through three's class of the same name, so parity is measured with nothing more. An addon is re-exported from `three/addons` by `tests/harness/three-addons.ts`, which names every value `src/addons` exports; another addon needs its line there, and its file in the pre-bundled lists of `vitest.config.ts` and `playground/vite.config.ts`.
4. **Constants** three has are all in `src/catalog/constants.ts` already; map the ones the class reads.

## The renderer facade

`src/renderer/PixiRenderer.ts` answers what core calls on a renderer:

- `init()` creates the pixi.js renderer on the canvas (`autoDetectRenderer`, WebGL first unless `preference: 'webgpu'`), with a transparent background unless `alpha: false`, as three's, and `useBackBuffer` passed through for pixi's advanced blend modes on WebGL. `backend.isWebGPUBackend` is set when pixi.js picks WebGPU.
- `setSize`, `setPixelRatio`, `getSize`, `getPixelRatio`, `setClearColor`, `setClearAlpha`, `clear`, `autoClear`, `domElement`.
- `render(scene, camera)` keeps a `Map<scene, View3D>`, making a view (and a pixi container holding it) the first time a scene is drawn. A HUD, portal or offscreen scene gets its own view instead of rebuilding one view every frame. When the camera is in the scene, the view draws with it; any other camera is copied each frame onto a proxy camera the facade adds to the scene (settings, and the transform relative to the scene).
- A view is freed when its scene is destroyed (the scene's `destroyed` event), or once the scene has gone `viewMaxIdleFrames` frames (120) undrawn, and made again if the scene is drawn later. A frame ends when some scene is drawn a second time, so a HUD component that owns a `new Scene()` stops holding a view after it unmounts while the main scene keeps drawing.
- `releaseView(scene)` frees a scene's view and leaves its children in place. `dispose()` frees every view and the pixi.js renderer.
- `getView(scene)` hands out the view for pixi-3d settings with no three counterpart: passes, environment, fog, culling.
- `setRenderTarget(target, face, mip)` points renders at a `WebGLRenderTarget`'s texture, or a face of a `WebGLCubeRenderTarget`, and `setViewport`, `setScissor` and `setScissorTest` take three's rects from the bottom-left corner. A view is placed on the viewport of the canvas or the target and sized to it. A clear covers the whole surface, or only the scissor rect while the scissor test is on, which two rects drawn before the scene (`ClearRect`) erase and fill, since pixi clears a whole surface or nothing. Into a target, tone mapping is off and exposure 1, as three draws a target in linear light, and the colour is stored with the 2.2 gamma pixi-3d decodes a colour map with, so a material sampling the target gets the linear colour back (`TARGET_OUTPUT` in `src/renderer/toneMapping.ts`); a camera whose `aspect` differs from the viewport's draws through the proxy, which projects with that aspect (`ProxyCamera`). pixi-3d's passes rebind a view's target at layer 0, so a cube face is drawn into a 2D texture and copied in upside down, the way cube faces are stored (`CubeFaceWriter`, `src/renderer/renderTargets.ts`). On WebGPU, pixi-3d binds the textures of every material a view draws with into the pass, hidden meshes' included, and WebGPU drops a pass that samples its own attachment, so a 2D target a material has sampled is drawn into a twin texture and copied into its own after the render (`TargetTwins`), freed with the target or the renderer. `readRenderTargetPixels` reads through pixi's extract on WebGL; `readRenderTargetPixelsAsync` maps a GPU buffer on WebGPU. Both decode pixi-3d's display encoding back to three's linear bytes.
- A scene whose `environment` is a texture, or whose `background` is a cube texture or one with an equirectangular `mapping`, goes through `EnvironmentMaps` (`src/environment/EnvironmentMaps.ts`), which the facade makes on first use and frees in `dispose()`. It bakes each source on the GPU, once per source and per picture of a cube target, into the linear cube three makes of it (an image cube mirrored in x, unless it is three's `CubeTexture`, which mirrors its images itself; an equirectangular map wrapped onto faces), and draws that cube behind the view as a pixi 2D mesh, with three's background rotation, intensity, PMREM blur and tone-mapping rules. For `environment` it bakes the source again, turned and scaled, into the 2.2-gamma cube pixi-3d's view prefilters. Its cubes are freed when the source is destroyed, after 120 frames unused, or with the facade.

three's renderer settings reach each view as it draws:

| three                                                                                  | pixi-3d                                                                                                                                                    |
| -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `toneMapping`, every curve three has, and `outputColorSpace`                           | The view's tone mapping bit is swapped for three's own curve and sRGB transfer function (none for `LinearSRGBColorSpace`), `src/renderer/toneMapping.ts`   |
| `toneMappingExposure`                                                                  | `view.exposure`; 1 with `NoToneMapping`, as three ignores it there                                                                                         |
| `shadowMap.type`: `BasicShadowMap`, `PCFShadowMap`, `PCFSoftShadowMap`, `VSMShadowMap` | `view.shadowFilter`: `'hard'`, `'pcf'`, `'pcf-high'`, `'pcf-high'`                                                                                         |
| `shadowMap.enabled`                                                                    | Lights cast shadows only while it's on (`canCastShadow` on the directional and spot aliases)                                                               |
| `light.shadow` (`mapSize`, `camera`, `bias`, `normalBias`)                             | Swapped for pixi-3d's own shadow settings while the view draws (`_prepareRender`); the largest `mapSize` sets `view.shadowQuality`                         |
| A hemisphere light                                                                     | `view.environment`, a pixi-3d `Hemisphere`, unless the scene has an `environment` (`src/renderer/sceneLights.ts`)                                          |
| `scene.background`: a three `Color` or a colour                                        | The canvas clears to it before the scene draws, untouched by tone mapping, as three's does                                                                 |
| `scene.background`: a 2D texture                                                       | A sprite just under the view, stretched over its rect, tinted by `backgroundIntensity` (`src/renderer/backdrop.ts`)                                        |
| `scene.background`: a cube or equirectangular texture; `scene.environment`             | `EnvironmentMaps`, above                                                                                                                                   |
| `scene.background`: anything else, such as a `Hemisphere`                              | `view.background`                                                                                                                                          |
| `scene.fog`: `Fog`, `FogExp2`                                                          | `view.fog`, with the view's fog bit swapped for one that mixes in after the tone curve, in a slot the tone mapping bit leaves (`src/renderer/sceneFog.ts`) |

Each frame the renderer also aims directional and spot lights at their targets and, for a soft-edged spot, moves pixi-3d's cone edges so its penumbra ramp follows three's, putting the lights' own values back once the view has drawn. A camera outside the drawn scene, or one whose `aspect` differs from its viewport's, is copied onto a `ProxyCamera` that projects with the source's `computeProjection` (`src/renderer/ProxyCamera.ts`); the catalog's cameras override `computeProjection` with three's projection.

The swaps reach two more pixi-3d internals, `View3D._toneMappingBit` and `View3D._fogBit`, set right after the public `toneMapping` and `fog` setters so pixi-3d queues its materials to rebuild. pixi-3d sets `_toneMappingBit` from its own curve again whenever it builds a view's render graph, on the view's first draw among others, so the facade makes it an accessor on each view that reads the three bit and ignores pixi-3d's writes (`holdToneMappingBit`).

## pixi.js 2D

pixi.js's 2D classes are elements of the same r3f tree as the 3D, under r3f's rules. `src/two-d/catalog.ts` exports each display class, filter, `GraphicsContext` and `Particle` under its class name with a `2D` suffix (`Sprite2D`, `HtmlText2D` for `HTMLText`), and `src/two-d/index.ts`, the area module, is spread into the catalog by one line of `catalog.ts`, so `<sprite2D>` resolves and is typed like `<mesh>`. The classes are pixi.js's own, not subclasses: a ref gets the pixi object, and an app imports the classes from `pixi.js`, so neither `react-pixi-fiber/three` nor `src/index.tsx` re-exports them. An app's own 2D class is registered with r3f's plain `extend({ Button2D: Button })`.

**The element surface.** The support's hooks add a 2D object where its element is among its siblings (`add2D`, and `addInElementOrder` with `indexByElementOrder` in `src/two-d/screen.ts`), so an insert or a keyed move goes through pixi's own `addChildAt`. `install2DSurface` (`src/two-d/surface.ts`) runs with the 3D patches when the first root loads the support, and gives pixi.js's classes what core and the hooks still read of an element's object:

- `Container`: `isObject3D`, a `uuid`, `traverse`, `traverseAncestors` and `dispose` (`destroy`).
- `filters` hands out a list that `attach="filters-0"` writes into and r3f's detach deletes from; each change sets the container's filters to the list without its gaps, since pixi freezes the array it keeps. `mask` reads `null` when unset, so a detach clears it, and a mask element with no parent is added as a child of what it masks, so its transform follows that object. `mask` also takes `setMask`'s options (`{ mask, inverse: true }`); options without a `mask` keep the current one.
- Methods that are props too: `cacheAsTexture` calls the method, `renderLayer` calls `layer.attach` or, with `null`, `detach`, and an `AnimatedSprite`'s `playing` calls `play()` or `stop()`.
- `Graphics` and `GraphicsContext` take a `draw` prop that clears and draws, run when a new function is passed.
- `Particle` is a child the `add` hook puts in a `ParticleContainer` (in element order) and `remove` takes out; `raycast` is `null`, so it never joins the interaction list.
- pixi's `Color` takes a three `Color` (`value` converts it with `toDisplayColor`), so `tint`, fills and filter colours take what a material's `color` takes.
- `GraphicsContext` and `Filter` get `dispose`, so unmounting frees what an element made. A `BlurFilter`'s `dispose` frees its two passes too. pixi's `destroy()` defaults leave a texture or a context passed in alone.

**The screen layer.** Each root's scene gets a screen layer (`ensureScreen`, by the root extension `react-pixi-fiber:screen` in `src/support/pixiSupport.ts`, which also puts it on `state.screen` and frees it on unmount); a portal's scene gets one when 2D first joins it. The `add` hook (and `Container3D.add`, for three code) sends a 2D object added to a scene to its screen layer, and anchors one added to any other 3D node (see "Bridges"); a 3D object under a 2D one is left out with a warning. The renderer facade draws the layer with the scene, with the scene's `View3D` in the layer's 3D layer (`layerOf`), a container at `VIEW_Z_INDEX`, just under 0: 2D at zIndex 0 and above draws over the 3D, below 0 behind it, and the layer sorts by zIndex. The stage is `ClearRect`, a texture or environment backdrop, then the screen layer. A scene whose children are only cameras, with no texture background or environment, gets no `View3D` until 3D joins it, and draws its screen layer over the clear.

**Frame jobs.** The screen extension also registers each root's 2D jobs with r3f's scheduler (`setupFrame2D` in `src/two-d/frame.ts`, released by `releaseFrame2D`). An `<animatedSprite2D>` is taken off pixi's shared ticker (`autoUpdate = false`, unless its element sets `autoUpdate`) when it joins a container, a scene or an anchor (`driveOnRootClock`), and the job `${rootId}_animatedSprites2D` advances it in the `update` phase, before the app's `useFrame` jobs, so it follows `frameloop="demand"`, `advance()` and a test's fixed clock; a playing sprite invalidates. Once an app registers pixi's `CullerPlugin` with `extensions.add`, the job `${rootId}_cull2D` culls `state.screen` against the canvas just before the render. Neither job allocates, and each returns at once while it has nothing to do.

**Events.** There is one event system, r3f's. A 2D element with a handler joins `internal.interaction` like a mesh; the `hitTest` hook (`hitTestScreen`, `src/two-d/hitTest.ts`) hit tests its screen layer once per pointer event (kept until the raycaster is next set, `castCount`), walking it front to back with pixi's `EventBoundary.hitPruneFn` and `hitTestFn`: `eventMode`, `hitArea`, masks, `interactiveChildren`, `visible`, `renderable` and `measurable`, with a handler alone making an element interactive. Each 2D hit under the element is an r3f intersection drawn over the view or under it, with its place from the front, so `compareHits` puts 2D in front first and 2D behind last, around every 3D hit, and r3f's bubbling, `stopPropagation`, capture and hover run across both. Its `distance` is 0. A hit carries `global` (the screen layer's live pointer, CSS pixels), `local` and `getLocalPosition`. `src/events/pointerEvents.ts` sets the canvas's cursor from the frontmost 2D element under the pointer on each move, and clears it when that element, or a container above it, is taken out of the tree (`clearCursorsUnder` in `src/two-d/cursor.ts`, from `remove` and `removeFromScene`). pixi's own `EventSystem` is off (`eventFeatures` all false in `PixiRenderer.init`): no pixi listeners fire and it never touches the cursor.

**Bridges.** Four ways across, in `src/two-d/Anchor2D.ts` and `src/two-d/bridges`, all exported from `src/index.tsx` (the guide is `src/two-d/__docs__/mixing-2d-and-3d.md`):

- `Anchor2D` (`<anchor2D>`, in the 2D area module) is a pixi container that follows a 3D node. `addToScene` sets its `_host` when it is added to a 3D node; a bare 2D object under a 3D node gets an anchor of its own (`adoptIntoAnchor`, freed by `releaseAnchor`). The facade calls `placeAnchors(scene, camera, view, layer)` in `render` after the camera is set and before the draw: each live anchor (an array, each anchor keeping its index) whose node is in the scene is put in the scene's 3D layer, projected with the camera's three matrices from `src/compat/cameraMatrices.ts`, and hidden (`renderable`) behind the camera, under a hidden ancestor, off the view (`hideOffscreen`) or behind 3D (`occlude`, a raycast). So it moves in the frame `useFrame` moved the 3D. A scene with no screen layer gets one when an anchor follows a node in it (`hasAnchorsIn`).
- `View3D` is a component: a `<container2D>` holding a portal scene's screen layer, whose 3D layer holds a pixi-3d `View3D` of the scene, and r3f's `createPortal` with the portal's camera and size. `PixiRenderer.embedView(view, scene, stage)` registers it; before every `_draw`, the facade gives each embedded view under the stage being drawn what `render` gives a scene's view (`_applySettings`, `_applySceneSettings`, a colour background as a backdrop sprite, `placeAnchors`) and puts its lights back after the draw. Before the draw, not in pixi's `onRender`, because baking an environment renders. pixi-3d's shaders leave out the alpha pixi gives a 2D object, so `_applySettings` draws any view whose global alpha is under 1, embedded or a scene's in a faded `<Layer3D>`, through an `AlphaFilter` of its own (`applyViewAlpha` in `src/renderer/viewAlpha.ts`, freed with the view).
- `Layer3D` is a component: a `<primitive>` of the scene's 3D layer, so its props and attached filters and mask apply to it. `add` and `remove` leave a 3D layer where it is, and the layout cleanup puts its props back. `createPointerEvents` casts the ray through the layer's inverse transform when it isn't the identity, so the 3D picks where it is drawn.
- `RenderTexture2D` is a component, as drei's `RenderTexture`: `useRenderTarget`, a portal scene of 2D drawn into the target in a `useFrame` (`frames`, `invalidate`), and a `<primitive>` of the target's texture attached to the parent, `map` by default.

Their events sort where they are drawn. A `<View3D>`'s screen layer is one entry in the parent screen layer's hit order (its `hitArea` is the view's rect). Its portal's `events.compute` (`computeEmbedded` in `src/two-d/hitTest.ts`) finds the pointer in the view, sets the portal's raycaster from its camera, and gives the raycaster the draw order of that entry (`setLayerOrder` in `src/events/hitOrder.ts`), which every hit in the portal starts with. Its 2D and 3D hits sort among themselves as on a root, and before the nested screen layer's own hit, as the container holding it, so the view's handlers and the 2D around it get an event after what is inside, as r3f bubbles from child to parent. A view's backdrops take no events. `<RenderTexture2D>`'s compute is drei's: the parent's raycaster hits the object, the hit's `uv` is the portal's pointer, and the portal's hits start with the draw order of that 3D hit, so they sort just before it. A nested screen layer is hit tested in global coordinates: `hitTestScreen` turns the portal's pointer through the screen layer's world transform.

**Loading.** `useTexture` returns three's `Texture`, which extends pixi's, so a sprite takes it as is. `AssetsLoader` (`src/two-d/AssetsLoader.ts`) is pixi's `Assets.load` in three's loader shape, for `useLoader`; `useAsset` is `useLoader(AssetsLoader, url)` typed.

## The entries and their types

The package has three entries, each a file of `src` that `package.json`, `tsdown.config.ts`, `tsconfig.json` and the Vite aliases name:

- `react-pixi-fiber`, `src/index.tsx`, mirrors the export list of r3f v10's `index.tsx`, which is everything `core/index.tsx` exports plus the entry's own `Canvas`, `createRoot`, `events`, `ThreeElements`, the build flags and the `ReactThreeFiber` namespace. Each value is core's own function, re-declared with a type from `src/types`, which names pixi-3d. It adds the pixi-3d side: `PixiRenderer`, `pixiSupport`, `catalog` and the compat types. `Environment`, `useEnvironment`, `useRenderTarget` and `useTextures` are our own implementations of r3f's, in `src/environment` and `src/loaders`, since r3f's reach three's loaders and renderers.
- `react-pixi-fiber/three`, `src/three.ts`, is what an r3f app imports from `three`: it re-exports every area module with `export *`. An app can alias `three` to it.
- `react-pixi-fiber/addons`, `src/addons/index.ts`, is what an r3f app imports from `three/addons`, re-exporting `src/addons/loaders`, `src/addons/controls` (`OrbitControls`, `MapControls`) and `src/addons/environment` (`HDRLoader`, `RGBELoader`). `GLTFLoader` parses a file with pixi-3d (`glbToGltf`, `normalizeMeshopt`, `loadImages` on a pixi `Loader` of its own, `parseGltf`) and builds three's `GLTF` from the catalog's classes, reading the node, skin and animation data pixi-3d parsed (`Scene3DSource._descriptor`, `source.animations`) and the file's JSON for names and `extras`. ## How a frame flows

1. `<Canvas>` measures its container and calls `createRoot(canvas).configure(props)`. The first configure loads the support (`loadPixiSupport`, which installs the compat patches, three's `Object3D` surface among them), registers the catalog as `getThree()`, constructs `PixiRenderer` with `{ canvas, antialias }` plus the `renderer` prop, sizes it and awaits `init()`. Core then creates the default `Raycaster`, camera (`PerspectiveCamera(50, 0, 0.1, 1000)` at z = 5, looking at the origin) and `Scene` from the catalog, adds the camera to the scene, sets ACES tone mapping and applies `shadows`.
2. `root.render(children)` mounts the tree with r3f's reconciler. Each element resolves to a catalog class, is constructed with `args`, gets its props through core's `applyProps`, and joins its parent through the support's `add` hook, before its sibling when inserted. Geometries and materials attach to the parent's `geometry` or `material` (`defaultAttach`). A 2D element directly in the canvas joins the scene's screen layer.
3. Every frame, `@pmndrs/scheduler` runs the root's jobs: deferred pointer raycasts, `useFrame` callbacks by phase, then the frustum job (`updateFrustum`, reading the camera's fresh matrices) and the visibility job (`Frustum.intersectsObject` for `onFramed` and `onVisible`), then the render job.
4. The render job calls `renderer.render(state.scene, state.camera)`. The facade finds or makes the scene's view (none while the scene has only 2D), puts the scene's screen layer in the stage with the view inside it, points it at the camera (or the proxy), puts a colour background on the canvas's clear colour, places the view on the viewport, swaps three's tone curve and output in, hands pixi-3d the lights' shadow settings and aims directional and spot lights at their targets, applies the fog, draws a texture background or bakes the environment, and calls `pixi.render()` on the view's container, into the canvas or the current render target. The lights' own settings are put back once it has drawn. pixi-3d's `View3D` runs its transform pass and draws.
5. A pointer event on the canvas reaches core's event layer (through `src/events/pointerEvents.ts`), which sets `state.pointer`, calls `raycaster.setFromCamera(pointer, camera)`, and asks the support's `hitTest` for the hits on each object that has a handler: the raycaster's on a 3D node, the screen layer's on a 2D element. `compareHits` sorts them by draw order, 2D over the 3D first and 2D behind it last; core bubbles them up the tree and hands them to the handlers as `ThreeEvent`s.
6. Unmounting removes each element through the `remove` hook and frees it through `dispose` (`destroy` for nodes, geometries and materials). Unmounting the root releases the renderer, whose `dispose()` frees every view and the pixi.js renderer.

## Measuring parity against three

Scenes, examples and docs import the library only as `react-pixi-fiber`, `react-pixi-fiber/three` and `react-pixi-fiber/addons`. `tsconfig.json` and the Vite aliases resolve those names to the entries in `src`. Pointing them at `src/r3f/src/legacy.tsx`, `three` and `tests/harness/three-addons.ts` instead renders the same scene file through r3f's own WebGL entry and real three.js. That is how parity is measured.

Two rules follow:

- A parity scene uses only names both sides export: r3f's API (`Canvas`, `useFrame`, `useThree`, ...), JSX elements, and the classes `react-pixi-fiber/three` shares with `three`. `PixiRenderer`, the catalog, pixi-3d's own names and the 2D elements are this package's only. A 2D or mixed scene has nothing to measure against: it lives in a 2D folder (`tests/scenes/2d`, `tests/scenes/mixed`, `examples/2d`), which the three.js side doesn't load, and is held to its own WebGL and WebGPU references.
- One renderer per page. Core keeps the registered namespace (`getThree()`) in a module variable, and the `extend()` registry and React context on `globalThis` under `Symbol.for` keys, so a pixi root and a three root in the same page would share them. Render each side in its own page or iframe: the harness runs the three.js pictures in a vitest project of their own and the playground builds each renderer in its own frame, both reading the two targets from `FIBER_TARGETS` in `scripts/test/aliases.mts` (`tests/README.md`).

## Upstream asks

None of these block us; with the renderer hooks of `src/r3f/README.md`, which also open the `kind` union and route `insertBefore` through the support's `add`, they would let the library run on published `@react-three/fiber` instead of a fork.

- A `/core` export of `createRoot(canvas, provider)` and `Canvas` with a `provider` prop.
- `Environment` loaded lazily or provided by the support, so `Canvas` doesn't pull three's addons.
- `getThree()` resolved per root from `state.internal.support`, so different renderers can share a page.
- A generic `RootState`, so a support can type it without re-declaring the hooks.
- A click-type event matched to its pointerdown when it has no `pointerId` (Chrome's `dblclick`), so `onDoubleClick` fires; our event layer does it for now.

pixi.js asks, found through the 2D:

- `BlurFilter.destroy` should destroy its two passes. They stay bound to the WebGPU renderer's uniform buffers; our `dispose` on `BlurFilter` frees them.
- `Renderer.destroy` frees the uniform batch pipe's buffers and the texture pool before the filter system, whose bind group still holds them, and each one warns `[BindGroup] a '...' was destroyed while still bound to a shader`. `PixiRenderer.dispose` destroys the filter system first. A filter still alive when the renderer goes warns the same way, and r3f disposes elements at idle priority, after a root's renderer is released, so unmounting a root whose tree has filters still logs these warnings on WebGPU.
