# Architecture

react-pixi-fiber renders react-three-fiber (r3f) v10 with pixi-3d, and pixi.js 2D in the same tree. r3f's core runs as a fork that asks the renderer support where it used to reach into three.js objects (the renderer hooks). `@react-fiber/core` gives every root one renderer support, which the packages above it fill through pixi.js's `extensions`: `@react-fiber/2d` with pixi.js's 2D, and `@react-fiber/threejs-compat` with @pixi/3d's objects and the three.js surface that r3f apps reach for. The goal is that an r3f app only swaps its imports, and that 2D is written the same way.

`docs/feasibility.md` has the findings this design rests on. `CODING_STANDARDS.md` says how the code is written.

```

packages/core/src/            @react-fiber/core

  extension.ts                @react-fiber/core/extension: the registry, the stage and the renderer parts packages use
  root/                       createRoot and <Canvas>, bound to the pixi provider
  support/                    the renderer support (kind 'pixi'), its registry and the hook dispatch
  renderer/                   PixiRenderer: r3f's renderer over pixi.js and View3Ds; render targets, backdrops, camera matrices
  stage/                      the screen layer, element order, cursors and 2D hit testing

  bridges/                    Anchor2D, View3D, Layer3D, RenderTexture2D
  hooks/                      useRenderTarget
```

## The packages

Each package is an npm workspace with its own `package.json`, `tsconfig.json` (extending `tsconfig.base.json`, whose paths name every package's sources) and `tsdown.config.ts`, and builds into its own `dist` (`npm run build` runs tsdown over the packages the root `tsdown.config.ts` lists). The graph is acyclic: r3f <- core <- 2d, 3d <- threejs-compat. A package imports another only through its entries; `npm run test:types` type-checks each package alone, against only the packages it depends on, which catches a package that leans on one above it.

- **`@react-fiber/r3f`** is the fork. Its own build is upstream's four entries, which import three; nothing of ours imports them but the parity harness.
- **`@react-fiber/core`** imports r3f's core modules by path (`@react-fiber/r3f/src/core/...`) and bundles them, so the packages above it share its one copy through its two entries: `.` for apps and `./extension` for packages.
- **`@react-fiber/2d`**, **`@react-fiber/threejs-compat`**: importing one registers it with core (below). threejs-compat's three entries all import `install.ts`, so `import { Vector3 } from '@react-fiber/threejs-compat/three'` installs it too. At this stage a root needs threejs-compat: it gives each root its default scene, camera and raycaster.
- **`@react-fiber/3d`** is a skeleton: `objects3D`, the renderer hooks of @pixi/3d's classes, which threejs-compat registers.

## The forked core

`packages/r3f` is `packages/fiber` of react-three-fiber (`src` and `types`) at the commit `scripts/repos/manifest.mts` pins, which `.repos/react-three-fiber` is checked out at. Its core asks the root's renderer support where it used to reach into three.js objects. `packages/r3f/README.md`, written for r3f's maintainers, gives the interface, each hook, what core did before and why. The whole change is `packages/r3f/fork.diff`: `npm run diff:r3f` writes it, `scripts/r3f/fork.mts --check` fails when it is stale and runs in `npm run test:lint`, and `git apply` takes it in an upstream checkout. r3f's own test suite passes on the fork as on upstream.

Besides the diff, the fork holds files of ours, listed in the script's `EXTRAS`:

- `react-reconciler/{index,constants}.{js,d.ts}`, at the relative path core imports. Upstream generates an ESM build of react-reconciler there at install time; ours re-exports the npm package, naming each constant, because `export *` from its CommonJS `constants` module loses exports under Vite.
- `package.json`: upstream's, named `@react-fiber/r3f`. The rename stays out of the diff, since upstream's workspace depends on the package as `@react-three/fiber`.
- `tsconfig.json` and `tsdown.config.ts`, the package's build.
- `README.md` (its diff size line is the script's) and `fork.diff`.

Core never imports `three` for a value. It reaches the renderer through these seams, and each is ours to fill:

- The renderer hooks (`RendererHooks` in `types/provider.d.ts`): `add` and `remove` for every tree change, `isInteractive` for which objects are nodes, `defaultAttach` and `applyProp` for props and attaches, `hitTest` and `compareHits` in the event pipeline, and `dispose`.
- `getThree()` (`core/three.ts`): `support.three` of the first root. Core builds its own objects from it: `Raycaster`, `Vector2`, `Vector3`, `Scene`, `PerspectiveCamera`, `Frustum`, and reads a few constants.
- `resolveConstructor()` (`core/extend.ts`): an element name resolves through `extend()` registrations, then `support.catalog` of the root's renderer.
- Duck typing that is left: `parent`, `visible`, `userData`, `raycast !== null`, and the members core calls on its own camera, raycaster and frustum. Core keys objects by ids it keeps (`getObjectId` in `core/utils/objectId.ts`), not by `uuid`, and finds the root of a hit object with no element by walking `parent`. Core never uses `instanceof`.

We use core's modules (root, reconciler, store, loop, events, portal, hooks) through `packages/core/src/index.tsx`. We don't use `core/components/Environment`, `core/hooks/useEnvironment` (three's addons) or `core/hooks/useRenderTarget` (it never disposes its target); threejs-compat's `environment` has adapted copies of the first two, and core's `hooks/useRenderTarget.ts` of the third. Nor do we use r3f's entries (`index.tsx`, `legacy.tsx`, `webgpu/`), `web/Canvas.tsx` (it imports Environment; `packages/core/src/root/Canvas.tsx` is its adapted copy) or `support/*` (three's renderers, with three's hooks in `support/threeHooks.ts`). They stay in the fork as upstream has them, but for the hooks. `legacy.tsx` and `support/webgl.ts` matter: the parity harness renders scenes through them.

## The registry

core knows no package above it. A package plugs in by registering with pixi.js's `extensions`, under the types `FiberExtensionType` names (`packages/core/src/support/registry.ts`, exported from `@react-fiber/core/extension`), when its entry is imported:

| Type      | `ref`                                                                       | What core does with it                                                                                                                              |
| --------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Objects` | `ObjectHooks`: `test(object)` and any of the renderer hooks                 | Keeps them by priority; the support asks the first whose `test` takes the object                                                                    |
| `Catalog` | classes by the PascalCase name of their element (`{ Sprite2D: Sprite }`)    | Merges them into `catalog`, one object a root's support holds as `catalog` and `three`, a higher priority's class replacing a lower one's of a name |
| `Support` | `SupportParts`: `Renderer`, `RenderTarget`, `CubeRenderTarget`, `install()` | The highest priority package's renderer and targets are the support's; each `install` runs once, when the first root loads the support              |

```ts
import { FiberExtensionType } from '@react-fiber/core/extension';
import { extensions } from 'pixi.js';

extensions.add(
  { type: FiberExtensionType.Catalog, name: '2d', ref: catalog2D },
  { type: FiberExtensionType.Objects, name: '2d', ref: objects2D },
  { type: FiberExtensionType.Support, name: '2d', ref: { install: () => registerRootExtension(frameExtension) } },
);
```

What registers today:

- **core** itself: `Anchor2D` in the catalog, at priority -1.
- **2d** (`packages/2d/src/index.ts`): the 2D classes; `objects2D`, the hooks of a pixi `Container`, `Particle`, `Filter` or `GraphicsContext`; and an `install` that registers each root's 2D frame jobs. It changes no pixi.js class.
- **threejs-compat** (`packages/threejs-compat/src/install.ts`): its catalog; `objects3D` from `@react-fiber/3d`; and `ThreeRenderer`, three's render targets and an `install` that runs `installObject3DSurface`.

Types follow the same split. core's types name the classes a root's objects are through `Registered<K>`: the class a package registers under `K` in the `Register` interface, or core's default from `RegisterDefaults` (@pixi/3d's `Container3D` for a scene, `Camera3D` for a camera, core's `PixiRenderer`, ...). threejs-compat augments `Register` with three's classes, so wherever it is installed `useThree().camera` is three's `PerspectiveCamera`, and a package adds its elements to `ThreeElements` the same way (`interface ThreeElements extends ThreeElementsOf<typeof catalog2D> {}`).

## The support

`packages/core/src/support/pixiSupport.ts` builds the object r3f's core loads when a root is configured, with the same shape as r3f's `support/webgpu.ts`, from what the packages registered:

| Field                              | Value                                                                                                                                                                                              |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kind`                             | `'pixi'`. Core's only branch on it tests for `'webgl'` (`core/renderer.ts`), so a pixi root takes the path that awaits the renderer's async `init()`, and the WebGL-only occlusion gate stays off. |
| `three`, `catalog`                 | The registry's `catalog`, for both: core builds its default raycaster, camera and scene from it, and element names resolve in it. threejs-compat's catalog (below) gives those classes.            |
| `Renderer`                         | The highest priority package's (`ThreeRenderer` with threejs-compat), else core's `PixiRenderer`.                                                                                                  |
| `RenderTarget`, `CubeRenderTarget` | The highest priority package's: `WebGLRenderTarget` and `WebGLCubeRenderTarget` with threejs-compat, which `useRenderTarget` and `<Environment>` make.                                             |
| `CanvasTarget`, `occlusion`        | Not available: pixi.js can't share a renderer between canvases, and pixi-3d has no occlusion queries.                                                                                              |
| The hooks                          | `pixiHooks` (`packages/core/src/support/hooks.ts`), below.                                                                                                                                         |

Each hook asks the `ObjectHooks` of the package that owns the object, the first whose `test` takes it: the child for `add` and `remove`, the object itself for the rest. `compareHits` is core's own.

- `add(parent, child, before)` and `remove`: 2d's hooks (`objects2D`) take a 2D object or a particle and add it under a 2D container where its element is among its siblings (`add2D`, `packages/2d/src/children.ts`), or under a 3D node through core's `addToScene` (the scene's screen layer, or an anchor), then put an animated sprite on its root's clock. @pixi/3d's hooks (`objects3D`, `packages/3d/src/objects3D.ts`, which threejs-compat registers) add a 3D node to a 3D node's children, through `addChildAt` before a sibling, and leave a 3D node under 2D out with a warning. `remove` mirrors them with `remove2D`, `removeFromScene` and `removeChild`.
- `isInteractive`: a `Container3D`, a pixi.js `Container` or a `Particle`. `defaultAttach`: `'geometry'` for a `Geometry3D`, `'material'` for a `BaseMaterial3D`.
- `applyProp`: 2d's hooks write the 2D props and attaches that aren't an assignment (`applyProp2D`, "pixi.js 2D" below); every other key, and every key of a 3D object, is core's to write.
- `hitTest`: a 2D element hit tests its screen layer (`hitTestScreen`, "pixi.js 2D" below); a 3D node casts the raycaster of its root or portal, and each hit takes its draw order in the 3D.
- `compareHits`: draw order (`packages/core/src/events/hitOrder.ts`). Each hit carries where it is drawn: pairs of a band (2D over the 3D, the 3D, 2D under it) and a place in it (a 2D object's place from the front, a 3D hit's distance), the outermost layer first. A portal drawn inside another layer starts with the order of what holds it, and a hit inside a layer sorts before the hit of what holds it, as a child's event comes before its parent's. `distance` stays the ray's.
- `dispose`: the owner's `dispose` hook when it has one, else the object's own `dispose`, which the compat layer gives pixi-3d's classes; a `Scene` is never freed. 2d's hook destroys a container, a graphics context or a filter with pixi's `destroy()`, and a `BlurFilter`'s two passes with it.

`packages/core/src/support/provider.ts` offers the support in the provider's `webgpu` slot, the one whose path awaits `init()`. The loader, `loadPixiSupport()`, first runs every registered package's `install` (threejs-compat's `installObject3DSurface()`, 2d's frame jobs, ...), so the prototype patches happen when the first root configures and never on import, and registers the root extension `react-fiber:screen`, which gives each root's scene its screen layer.

Where core builds objects of its own outside r3f's core, for the bridges and 2D hits, it takes the classes from the root's support as r3f's core does (`classesOf` in `packages/core/src/support/classes.ts`): a `<View3D>`'s scene and camera, a `<RenderTexture2D>`'s scene, an anchor's occlusion raycaster, a 2D hit's `point`. Those classes take three's arguments and have three's members, the ones r3f's core calls on its own.

`packages/core/src/root/createRoot.ts` wraps core's `createRoot(canvas, provider)`. Its `configure` reads `gl` as `renderer`, so code written for `@react-three/fiber/legacy` runs, and forces `share: false`: pixi.js can't draw one renderer into several canvases, so every canvas gets its own and `primary` is ignored.

`packages/core/src/root/Canvas.tsx` is r3f's `web/Canvas.tsx`, adapted: same measuring, Suspense blocking, error boundary, event wiring and teardown, without three's `<Environment>`. `background` takes a colour, which it puts on `scene.background`.

## The compat layer

`packages/threejs-compat/src/compat/installObject3DSurface.ts` patches pixi-3d's prototypes once, so every node answers core's duck-typed checks and three's API, including nodes pixi-3d builds itself (glTF nodes passed to `<primitive>`):

- `Container3D` gets three's `Object3D` surface (`Object3DMembers`): `isObject3D`, `id` and `uuid` (from `uid`), `name` (over `label`), `type`, `userData`, `up`, `add`, `remove`, `clear`, `attach` (pixi-3d's `reparentChild`), `traverse`, `traverseVisible`, `traverseAncestors`, `getObjectByName`, `getObjectById`, `getObjectByProperty`, `getWorldPosition`, `getWorldQuaternion`, `getWorldScale`, `getWorldDirection`, `localToWorld`, `worldToLocal`, `rotateX`/`Y`/`Z`/`OnAxis`/`OnWorldAxis`, `translateX`/`Y`/`Z`/`OnAxis`, `applyMatrix4`, `applyQuaternion`, the `setRotationFrom*` methods, `lookAt(x, y, z)` (keeping `up`; cameras and lights face it with -Z, as pixi-3d's do), `raycast` (a no-op) and `dispose` (`destroy`). `renderOrder` and `frustumCulled` are kept and inert.
- `rotation` is replaced with an `Euler` (`packages/threejs-compat/src/math/Euler.ts`) per node, made on first read from the quaternion. Writing it writes the quaternion through its order; any change to the quaternion (`set`, `slerp`, `lookAt`, an animation) writes the angles back, through a wrapper on `Container3D._onUpdate`, the callback a node's vectors call when they change. pixi-3d's own XYZ `rotation` is never written. `angle` is a degree view over the same `Euler`.
- `matrix` is pixi-3d's `localTransform`, built from the components when read. `matrixAutoUpdate = false` gives the node an own `updateLocalTransform` that does nothing, so the transform pass keeps the matrix as set; reading `matrix` marks the node's transform changed (`_onUpdate()`), so an edit through it shows next frame. `updateMatrix` builds it from the components on demand. `matrixWorld` is worked out when read; `updateMatrixWorld` and `updateWorldMatrix` are no-ops.
- `ObservableVector3` (a node's `position` and `scale`), `ObservableQuaternion` and pixi-3d's `Matrix4` get the members three's classes have and pixi-3d's lack, copied from the classes in `packages/threejs-compat/src/math` (the `*_MEMBERS` lists beside them), and typed by the interfaces in `packages/threejs-compat/src/compat/threeMembers.ts`. `ObservableQuaternion.setFromEuler` reads an Euler's order. The matrix members that take other arguments in three (`setPosition(x, y, z)`, `makeTranslation(vector)`, `toArray(array, offset)`) fall back to pixi-3d's for pixi-3d's arguments.
- `Mesh3D.raycast`: three's `Mesh.raycast`, ported over the geometry's attributes, installed by `installRaycasting` in `packages/threejs-compat/src/compat/Raycaster.ts`.
- `BaseMaterial3D`'s `_deriveLayoutFromBits`, `_setTextureSlot` and `destroy` are wrapped by `installTextureTracking` (`packages/threejs-compat/src/catalog/textures/textureTransform.ts`), so each three `Texture` knows the materials that hold it. A change to its `offset`, `repeat`, `rotation`, `center` or `flipY` rewrites the material's `uvTransform`, pixi-3d's one UV transform per material, from the material's `map` (or its first three texture). `flipY` folds in there: the catalog's geometries give three's UVs upside down, which a flipped image matches, so a texture with `flipY` off, such as a `DataTexture`, gets a flip; a glTF texture, on glTF's own UVs, gets one only with `flipY` on.
- `Camera3D`: `isCamera`, `isPerspectiveCamera`, `isOrthographicCamera`, `type`, a `getWorldDirection` along -Z, and `projectionMatrix`, `projectionMatrixInverse`, `matrixWorldInverse` worked out when read (`cameraMatrices.ts`). pixi-3d fills `camera.projection` and `camera.view` only while drawing, so they're a frame old between frames and identity before the first one.
- `Mesh3D`, `Sprite3D`, `Model3D` and `Light` get three's `is*` flags and `type`; pixi-3d's lights keep their own `type`, which their shaders read.
- `Geometry3D.isBufferGeometry`, `BaseMaterial3D.isMaterial`, three's flags, and `dispose` on both, which the `dispose` hook calls when an element unmounts.
- `BaseMaterial3D` gets three's `Material` fields (`MaterialMembers`, `installMaterialSurface` in `packages/threejs-compat/src/compat/materialSurface.ts`): `side`, `transparent`, `opacity`, `alphaTest`, `depthTest`, `depthWrite`, `blending`, `visible`, `polygonOffset`, `toneMapped` (pixi-3d's `_skipsToneCurve`, inverted, which ends the shader with pixi-3d's sRGB encode alone) and `needsUpdate` drive pixi-3d's state and shader at any time, for a glTF model's materials too. Each change rebuilds the meshes' shaders and asks every view drawing the material to record its draws again, since pixi-3d's default passes keep replaying recorded draws. three code often builds materials at module scope, so the first catalog material installs the surface too, if no root has yet.
- `Mesh3D.defaultOptions` gets a placeholder geometry and material, because core constructs `<mesh3D>` with no arguments and attaches them afterwards. The placeholder geometry is a zero-size box, which draws and picks nothing, like three's empty `BufferGeometry`.

The patches are typed: `PixiMixins.Container3D` and the `@pixi/3d` module are augmented with `Object3DMembers`, `CameraMembers` and the `Three*Members` interfaces. A type can't narrow what pixi-3d's classes declare, so the catalog's node classes re-declare `rotation` as an `Euler` and `lookAt` with three's arguments (`lookAtPoint`); on pixi-3d's own classes the types stay pixi-3d's and the values are the same.

The patches reach a few of pixi-3d's internals: `_onUpdate` (to mark a node changed and to follow its quaternion), `_localTransformDirty` and `rotationDirty`. Each is a candidate for a public pixi-3d API (`docs/feasibility.md`, section 6).

The `Raycaster` (`packages/threejs-compat/src/compat/Raycaster.ts`) builds its ray from the camera's own matrices (any camera picks, not only one a view draws with), walks objects through their `raycast` method as three does, and returns three's intersection shape: `distance`, `point`, `object`, `face` (`a`, `b`, `c`, `normal`), `faceIndex`, `barycoord`, `uv`, `normal`, `instanceId`. A mesh's `raycast` is three r187's `Mesh.raycast`: a bounding sphere and box test, then three's watertight triangle test on every triangle, read through the position attribute's stride and offset, so every triangle the ray crosses is a hit. The loop runs in `crossTriangles` over typed arrays and numbers, so it allocates nothing per triangle. As in three, hidden objects are hit, and the material's `side` (or pixi-3d's `doubleSided`) decides which faces count. A `BufferGeometry` hands pixi-3d `1 - v`, so its hits report `uv` turned back. `Points`, `Line`, `LineSegments`, `LineLoop` and `Sprite` have `raycast` methods of their own (`packages/threejs-compat/src/catalog/drawables/raycastDrawables.ts`), three's, with `raycaster.params` thresholds and `index` and `distanceToRay` on their hits; the event layer reaches them as it reaches meshes. There are no `layers`.

`packages/core/src/events/pointerEvents.ts` is the event layer `<Canvas>` and the `events` export use: r3f's `createPointerEvents`, with `onDoubleClick` given the last pointerdown's `pointerId`, since r3f v10 keys pointerdown hits by it and Chrome's `dblclick` has none.

The `Raycaster` counts every time it is set (`noteCast`, core's), which is how a screen layer's hit test knows a new pointer event began.

`InstancedMesh` (`packages/threejs-compat/src/catalog/instancing`) extends pixi-3d's `BatchedMesh3D`, one slot per instance. `setMatrixAt` and `setColorAt` write the slot and three's arrays; `needsUpdate` copies the arrays after direct writes. Instance colours live in the batch's instance data, and a material can only read instance data through a shader bit fixed when it is built, so the slots draw with a twin of the material (`instanceColorMaterial.ts`): the same class with the colour bit in front of its bits, kept in step through the material's `update` and `_setTextureSlot`, and freed with the last mesh that uses it.

## The math

`packages/threejs-compat/src/math` has three's math classes, which `@react-fiber/threejs-compat/three` exports and the catalog registers under the names core builds by (`Vector3`, `Frustum`, ...). Each extends pixi-3d's class of the same kind (`Vector3`, `Quaternion`, `Matrix4`, `Box` as `Box3`, `Sphere`, `Ray`, `Plane`, `Spherical`, `Frustum`) and adds what three has and pixi-3d lacks, so pixi-3d takes them wherever it takes its own; pixi-3d's methods already take three's arguments, with an optional `out` last. `Euler` extends `ObservableVector3`, so a node's `rotation` can be one. `Color` is three's, with three's colour management (`ColorManagement`): channels in linear sRGB, CSS colours and hex numbers read as sRGB. `toPixiColor` hands a `Color` to pixi-3d as the display `ColorSource` pixi-3d decodes back to the same linear values, encoded with pixi-3d's own `linearToSrgb`; `toDisplayColor` encodes it to sRGB as three outputs it, for what pixi.js draws without decoding, such as a clear colour or a 2D tint. `MathUtils` and `Clock` are three's.

## The catalog

`packages/threejs-compat/src/catalog/catalog.ts` builds the namespace core reads as `getThree()` and resolves element names in: pixi-3d's exports, then the three-named classes of every area module, then three's constants.

- pixi-3d's own names stay reachable: `<mesh3D>`, `<cubeGeometry>`, `<material3D>`, `<flatMaterial>`, with pixi-3d's options-object constructors.
- Three-named aliases win over pixi-3d classes of the same name (`SphereGeometry`, `AmbientLight`, `DirectionalLight`, `PointLight`, `PlaneGeometry`, `Vector3`, ...), whose options-object constructors would ignore three's positional `args`. Each alias extends the pixi-3d class, takes three's constructor and defaults, and renames fields (`color` over `baseColor`, `metalness` over `metallic`, `opacity` over `alpha`, `transparent` over `alphaMode`).
- A material's `color` and `emissive` are three `Color`s that write pixi-3d's `baseColor` and emissive colour on every change. `MeshStandardMaterial` is built with pixi-3d's emissive feature on, black until set, since pixi-3d can't turn it on later.
- Every geometry is a `BufferGeometry` (`packages/threejs-compat/src/catalog/geometries`), a `Geometry3D` built by three's own generator. It keeps three's attributes beside pixi-3d's: `attributes` is a proxy that reads and writes three's names and iterates pixi-3d's. `position`, `normal`, `uv` (as `1 - v`, since three flips images on load), `color` and `tangent` are drawn. A change packs the geometry into pixi-3d's shared buffers again, or, under `DynamicDrawUsage`, it draws from its own. Points and lines set its draw mode: a camera-facing quad per point, or vertex pairs as lines.
- The standard and physical materials swap pixi-3d's PBR material and lighting bits for three's (`threeStandardBits.ts`) in `getPrimaryDescriptor`; each catalog material also adds a normal flip for `BackSide` (`threeDescriptor`) and works in linear light (`colorSpace: 'linear'`), where pixi-3d's `FlatMaterial` works on colours as authored. `MeshNormalMaterial` takes pixi-3d's display path instead, which leaves its colour unencoded, as three's. `MeshPhysicalMaterial` lays pixi-3d's features out again when one is first set before the first draw.
- `DirectionalLight` starts one unit up and shines at its `target`, as three's does; the renderer turns it toward the target before each frame, since pixi-3d's light shines along its local -Z.
- `PerspectiveCamera` and `OrthographicCamera` override pixi-3d's `computeProjection` with three's projection, built from the settings `updateProjectionMatrix` last saw (core calls it on every resize): a camera's own `aspect`, `zoom`, film offset, view offset and off-centre orthographic bounds. Lights carry three's `LightShadow` classes and three `Color`s.

The classes live in area modules, each a folder with an `index.ts` that exports its classes by name. `catalog.ts` spreads every area module into the namespace, and `packages/threejs-compat/src/three.ts` re-exports each with `export *`, so a class an area module exports is in the catalog, has a JSX element and is exported from `@react-fiber/threejs-compat/three` at once:

| Area module                                                                                                                                        | Holds                                                                                                                                                   |
| -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |

### Adding to the catalog

1. **The class.** Write it in its own file in its area's folder (`packages/threejs-compat/src/catalog/lights/SpotLight.ts`), under three's name, with three's constructor and defaults, extending the pixi-3d class it maps to. Its JSDoc says what differs from three. A node class (one that extends a pixi-3d `Container3D`) re-declares `rotation` as an `Euler` and `lookAt` with three's arguments, as `packages/threejs-compat/src/catalog/objects/Mesh.ts` does. Colour fields are three `Color`s handed to pixi-3d with `toPixiColor`, as `packages/threejs-compat/src/catalog/materials/MeshStandardMaterial.ts` does.
2. **Its export.** Add one line to the area's `index.ts`: `export { SpotLight } from './SpotLight';`. That puts it in the catalog, gives it an element (`<spotLight>`) typed from its class, and exports it from `@react-fiber/threejs-compat/three`. Nothing else is shared: `catalog.ts`, `three.ts` and the package's `index.ts` don't change. A class for `@react-fiber/threejs-compat/addons` goes in `packages/threejs-compat/src/addons/loaders`, `packages/threejs-compat/src/addons/controls` or `packages/threejs-compat/src/addons/environment` the same way. Two areas never export the same name: `packages/threejs-compat/src/three.ts` would see a duplicate `export *`.
3. **Its three counterpart.** A scene that uses the element or imports the class from `@react-fiber/threejs-compat/three` renders through three's class of the same name, so parity is measured with nothing more. An addon is re-exported from `three/addons` by `tests/harness/three-addons.ts`, which names every value `packages/threejs-compat/src/addons` exports; another addon needs its line there, and its file in the pre-bundled lists of `vitest.config.ts` and `playground/vite.config.ts`.
4. **Constants** three has are all in `packages/threejs-compat/src/catalog/constants.ts` already; map the ones the class reads.

## The renderer facade

The renderer is in two parts. core's `PixiRenderer` (`packages/core/src/renderer/PixiRenderer.ts`) draws scenes and the stage: the pixi.js renderer, a view per scene, the screen layer, anchors, embedded views, render targets, clears and colour backgrounds. threejs-compat's `ThreeRenderer` (`packages/threejs-compat/src/renderer/ThreeRenderer.ts`) extends it with three's settings, through the protected methods `PixiRenderer` calls as a view draws: `_applySettings` (tone mapping, shadows, `EnvironmentMaps`), `_applySceneSettings` (lights, fog, a texture background), `_finishView` (puts the lights back), `_backgroundColor` (a three `Color` background), `_releaseSettings` and `_disposeSettings`, and adds three's `readRenderTargetPixels`. `toneMapping`, `toneMappingExposure`, `outputColorSpace` and `shadowMap` live on `PixiRenderer`, since r3f's core writes them on any renderer; `ThreeRenderer` draws with them. Together they answer what core calls on a renderer:

- `init()` creates the pixi.js renderer on the canvas (`autoDetectRenderer`, WebGL first unless `preference: 'webgpu'`), with a transparent background unless `alpha: false`, as three's, and `useBackBuffer` passed through for pixi's advanced blend modes on WebGL. `backend.isWebGPUBackend` is set when pixi.js picks WebGPU.
- `setSize`, `setPixelRatio`, `getSize`, `getPixelRatio`, `setClearColor`, `setClearAlpha`, `clear`, `autoClear`, `domElement`.
- `render(scene, camera)` keeps a `Map<scene, View3D>`, making a view (and a pixi container holding it) the first time a scene is drawn. A HUD, portal or offscreen scene gets its own view instead of rebuilding one view every frame. When the camera is in the scene, the view draws with it; any other camera is copied each frame onto a proxy camera the facade adds to the scene (settings, and the transform relative to the scene).
- A view is freed when its scene is destroyed (the scene's `destroyed` event), or once the scene has gone `viewMaxIdleFrames` frames (120) undrawn, and made again if the scene is drawn later. A frame ends when some scene is drawn a second time, so a HUD component that owns a `new Scene()` stops holding a view after it unmounts while the main scene keeps drawing.
- `releaseView(scene)` frees a scene's view and leaves its children in place. `dispose()` frees every view and the pixi.js renderer.
- `getView(scene)` hands out the view for pixi-3d settings with no three counterpart: passes, environment, fog, culling.
- `setRenderTarget(target, face, mip)` points renders at a `WebGLRenderTarget`'s texture, or a face of a `WebGLCubeRenderTarget`, and `setViewport`, `setScissor` and `setScissorTest` take three's rects from the bottom-left corner. A view is placed on the viewport of the canvas or the target and sized to it. A clear covers the whole surface, or only the scissor rect while the scissor test is on, which two rects drawn before the scene (`ClearRect`) erase and fill, since pixi clears a whole surface or nothing. Into a target, tone mapping is off and exposure 1, as three draws a target in linear light, and the colour is stored with the 2.2 gamma pixi-3d decodes a colour map with, so a material sampling the target gets the linear colour back (`TARGET_OUTPUT` in `packages/threejs-compat/src/renderer/toneMapping.ts`); a camera whose `aspect` differs from the viewport's draws through the proxy, which projects with that aspect (`ProxyCamera`). pixi-3d's passes rebind a view's target at layer 0, so a cube face is drawn into a 2D texture and copied in upside down, the way cube faces are stored (`CubeFaceWriter`, `packages/core/src/renderer/renderTargets.ts`). On WebGPU, pixi-3d binds the textures of every material a view draws with into the pass, hidden meshes' included, and WebGPU drops a pass that samples its own attachment, so a 2D target a material has sampled is drawn into a twin texture and copied into its own after the render (`TargetTwins`), freed with the target or the renderer. `ThreeRenderer`'s `readRenderTargetPixels` reads through pixi's extract on WebGL; `readRenderTargetPixelsAsync` maps a GPU buffer on WebGPU. Both decode pixi-3d's display encoding back to three's linear bytes.
- A scene whose `environment` is a texture, or whose `background` is a cube texture or one with an equirectangular `mapping`, goes through `EnvironmentMaps` (`packages/threejs-compat/src/environment/EnvironmentMaps.ts`), which the facade makes on first use and frees in `dispose()`. It bakes each source on the GPU, once per source and per picture of a cube target, into the linear cube three makes of it (an image cube mirrored in x, unless it is three's `CubeTexture`, which mirrors its images itself; an equirectangular map wrapped onto faces), and draws that cube behind the view as a pixi 2D mesh, with three's background rotation, intensity, PMREM blur and tone-mapping rules. For `environment` it bakes the source again, turned and scaled, into the 2.2-gamma cube pixi-3d's view prefilters. Its cubes are freed when the source is destroyed, after 120 frames unused, or with the facade.

three's renderer settings reach each view as it draws, through `ThreeRenderer`:

| three                                                                                  | pixi-3d                                                                                                                                                                            |
| -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `toneMapping`, every curve three has, and `outputColorSpace`                           | The view's tone mapping bit is swapped for three's own curve and sRGB transfer function (none for `LinearSRGBColorSpace`), `packages/threejs-compat/src/renderer/toneMapping.ts`   |
| `toneMappingExposure`                                                                  | `view.exposure`; 1 with `NoToneMapping`, as three ignores it there                                                                                                                 |
| `shadowMap.type`: `BasicShadowMap`, `PCFShadowMap`, `PCFSoftShadowMap`, `VSMShadowMap` | `view.shadowFilter`: `'hard'`, `'pcf'`, `'pcf-high'`, `'pcf-high'`                                                                                                                 |
| `shadowMap.enabled`                                                                    | Lights cast shadows only while it's on (`canCastShadow` on the directional and spot aliases)                                                                                       |
| `light.shadow` (`mapSize`, `camera`, `bias`, `normalBias`)                             | Swapped for pixi-3d's own shadow settings while the view draws (`_prepareRender`); the largest `mapSize` sets `view.shadowQuality`                                                 |
| A hemisphere light                                                                     | `view.environment`, a pixi-3d `Hemisphere`, unless the scene has an `environment` (`packages/threejs-compat/src/renderer/sceneLights.ts`)                                          |
| `scene.background`: a three `Color` or a colour                                        | The canvas clears to it before the scene draws, untouched by tone mapping, as three's does                                                                                         |
| `scene.background`: a 2D texture                                                       | A sprite just under the view, stretched over its rect, tinted by `backgroundIntensity` (`packages/core/src/renderer/backdrop.ts`)                                                  |
| `scene.background`: a cube or equirectangular texture; `scene.environment`             | `EnvironmentMaps`, above                                                                                                                                                           |
| `scene.background`: anything else, such as a `Hemisphere`                              | `view.background`                                                                                                                                                                  |
| `scene.fog`: `Fog`, `FogExp2`                                                          | `view.fog`, with the view's fog bit swapped for one that mixes in after the tone curve, in a slot the tone mapping bit leaves (`packages/threejs-compat/src/renderer/sceneFog.ts`) |

Each frame the renderer also aims directional and spot lights at their targets and, for a soft-edged spot, moves pixi-3d's cone edges so its penumbra ramp follows three's, putting the lights' own values back once the view has drawn. A camera outside the drawn scene, or one whose `aspect` differs from its viewport's, is copied onto a `ProxyCamera` that projects with the source's `computeProjection` (`packages/core/src/renderer/ProxyCamera.ts`); the catalog's cameras override `computeProjection` with three's projection.

The swaps reach two more pixi-3d internals, `View3D._toneMappingBit` and `View3D._fogBit`, set right after the public `toneMapping` and `fog` setters so pixi-3d queues its materials to rebuild. pixi-3d sets `_toneMappingBit` from its own curve again whenever it builds a view's render graph, on the view's first draw among others, so the facade makes it an accessor on each view that reads the three bit and ignores pixi-3d's writes (`holdToneMappingBit`).

## pixi.js 2D

pixi.js's 2D classes are elements of the same r3f tree as the 3D, under r3f's rules. `packages/2d/src/catalog.ts` exports each display class, filter, `GraphicsContext` and `Particle` under its class name with a `2D` suffix (`Sprite2D`, `HtmlText2D` for `HTMLText`), and `packages/2d/src/index.ts`, the package's entry, registers them as a catalog and adds them to `ThreeElements`, so `<sprite2D>` resolves and is typed like `<mesh>`. The classes are pixi.js's own, not subclasses: a ref gets the pixi object, and an app imports the classes from `pixi.js`, so no entry re-exports them. The entry exports `useAsset` and `AssetsLoader`; the 2D types (`ThreeEvent2D`, `Intersection2D`, ...) are core's, since its element and event types read them. An app's own 2D class is registered with r3f's plain `extend({ Button2D: Button })`.

**The element surface.** pixi.js's classes stay as pixi.js made them: 2d patches no prototype, and `tests/unit/pixi-prototypes.test.tsx` holds it to that. What r3f's core reads of an element's object is in core's fork (ids it keeps, `parent`) or in 2d's hooks, `objects2D` (`packages/2d/src/objects2D.ts`):

- `add` and `remove` put a 2D object where its element is among its siblings (`add2D`, and `addInElementOrder` with `indexByElementOrder` in `packages/core/src/stage/screen.ts`), so an insert or a keyed move goes through pixi's own `addChildAt`. A `Particle` goes in a `ParticleContainer`, in element order.
- `isInteractive` takes a `Container` or a `Particle`; a filter and a graphics context attach.
- `dispose` destroys a container, a graphics context or a filter with pixi's `destroy()`, whose defaults leave a texture or a context passed in alone, and a `BlurFilter`'s two passes with it.
- `applyProp` (`applyProp2D`, `packages/2d/src/props.ts`) writes the props and attaches an assignment can't:
  - `filters` and `attach="filters-N"`: 2d keeps each container's filters as a list by slot, which a filter element writes into and its detach empties, and sets the container's filters to the list without its gaps, since pixi keeps a frozen copy.
  - `mask` and `attach="mask"`: a detach clears the mask, which r3f's `delete` can't, since pixi's getter reads `undefined` when unset. A mask element with no parent, as an attached one is, becomes a child of what it masks, so its transform follows that object. `mask` also takes `setMask`'s options (`{ mask, inverse: true }`); options without a `mask` keep the current one.
  - Methods that are props: `cacheAsTexture` calls the method, `parentRenderLayer` calls `layer.attach` or, with `null`, `detach`, and an `AnimatedSprite`'s `playing`, whose getter is read-only, calls `play()` or `stop()`.
  - `draw` on a `Graphics` or a `GraphicsContext` clears it and draws, when a new function is passed.

A colour prop takes what pixi's `Color` takes. A three `Color` isn't one: pixi reads its channels as 0 to 255, so convert it, with `getHex()` or `getStyle()`.

**The screen layer.** The screen layer is core's stage. Each root's scene gets one (`ensureScreen`, by the root extension `react-fiber:screen` in `packages/core/src/support/pixiSupport.ts`, which also puts it on `state.screen` and frees it on unmount); a portal's scene gets one when 2D first joins it. The `add` hook (and `Container3D.add`, for three code) sends a 2D object added to a scene to its screen layer, and anchors one added to any other 3D node (see "Bridges"); a 3D object under a 2D one is left out with a warning. The renderer facade draws the layer with the scene, with the scene's `View3D` in the layer's 3D layer (`layerOf`), a container at `VIEW_Z_INDEX`, just under 0: 2D at zIndex 0 and above draws over the 3D, below 0 behind it, and the layer sorts by zIndex. The stage is `ClearRect`, a texture or environment backdrop, then the screen layer. A scene whose children are only cameras, with no texture background or environment, gets no `View3D` until 3D joins it, and draws its screen layer over the clear.

**Frame jobs.** 2d's root extension `react-fiber:frame2D`, which its `install` registers, gives each root its 2D jobs in r3f's scheduler (`setupFrame2D` in `packages/2d/src/frame.ts`, released by `releaseFrame2D`). An `<animatedSprite2D>` is taken off pixi's shared ticker (`autoUpdate = false`, unless its element sets `autoUpdate`) when it joins a container, a scene or an anchor (`driveOnRootClock`), and the job `${rootId}_animatedSprites2D` advances it in the `update` phase, before the app's `useFrame` jobs, so it follows `frameloop="demand"`, `advance()` and a test's fixed clock; a playing sprite invalidates. Once an app registers pixi's `CullerPlugin` with `extensions.add`, the job `${rootId}_cull2D` culls `state.screen` against the canvas just before the render. Neither job allocates, and each returns at once while it has nothing to do.

**Events.** There is one event system, r3f's. A 2D element with a handler joins `internal.interaction` like a mesh; the `hitTest` hook (`hitTestScreen`, `packages/core/src/stage/hitTest.ts`) hit tests its screen layer once per pointer event (kept until a raycaster is next set, which the raycaster counts with core's `noteCast`), walking it front to back with pixi's `EventBoundary.hitPruneFn` and `hitTestFn`: `eventMode`, `hitArea`, masks, `interactiveChildren`, `visible`, `renderable` and `measurable`, with a handler alone making an element interactive. Each 2D hit under the element is an r3f intersection drawn over the view or under it, with its place from the front, so `compareHits` puts 2D in front first and 2D behind last, around every 3D hit, and r3f's bubbling, `stopPropagation`, capture and hover run across both. Its `distance` is 0. A hit carries `global` (the screen layer's live pointer, CSS pixels), `local` and `getLocalPosition`. `packages/core/src/events/pointerEvents.ts` sets the canvas's cursor from the frontmost 2D element under the pointer on each move, and clears it when that element, or a container above it, is taken out of the tree (`clearCursorsUnder` in `packages/core/src/stage/cursor.ts`, from `remove` and `removeFromScene`). pixi's own `EventSystem` is off (`eventFeatures` all false in `PixiRenderer.init`): no pixi listeners fire and it never touches the cursor.

**Bridges.** Four ways across, in `packages/core/src/bridges`, all exported from `@react-fiber/core` (the guide is `packages/2d/src/__docs__/mixing-2d-and-3d.md`). They are core's, since the stage and the renderer place and draw them, and they need 2d installed, since what they hold is 2D. They build their scenes, cameras and raycasters from the root's support (`classesOf`), so they draw whatever 3D the registered packages give:

- `Anchor2D` (`<anchor2D>`, which core registers in the catalog) is a pixi container that follows a 3D node. `addToScene` sets its `_host` when it is added to a 3D node; a bare 2D object under a 3D node gets an anchor of its own (`adoptIntoAnchor`, freed by `releaseAnchor`). The facade calls `placeAnchors(scene, camera, view, layer)` in `render` after the camera is set and before the draw: each live anchor (an array, each anchor keeping its index) whose node is in the scene is put in the scene's 3D layer, projected with the camera's three matrices from `packages/core/src/renderer/cameraMatrices.ts`, and hidden (`renderable`) behind the camera, under a hidden ancestor, off the view (`hideOffscreen`) or behind 3D (`occlude`, a raycast). So it moves in the frame `useFrame` moved the 3D. A scene with no screen layer gets one when an anchor follows a node in it (`hasAnchorsIn`).
- `View3D` is a component: a pixi container, as a `<primitive>`, holding a portal scene's screen layer, whose 3D layer holds a pixi-3d `View3D` of the scene, and r3f's `createPortal` with the portal's camera and size. `PixiRenderer.embedView(view, scene, stage)` registers it; before every `_draw`, the facade gives each embedded view under the stage being drawn what `render` gives a scene's view (`_applySettings`, `_applySceneSettings`, a colour background as a backdrop sprite, `placeAnchors`) and puts its lights back after the draw. Before the draw, not in pixi's `onRender`, because baking an environment renders. pixi-3d's shaders leave out the alpha pixi gives a 2D object, so `_applySettings` draws any view whose global alpha is under 1, embedded or a scene's in a faded `<Layer3D>`, through an `AlphaFilter` of its own (`applyViewAlpha` in `packages/core/src/renderer/viewAlpha.ts`, freed with the view).
- `Layer3D` is a component: a `<primitive>` of the scene's 3D layer, so its props and attached filters and mask apply to it. `add` and `remove` leave a 3D layer where it is, and the layout cleanup puts its props back. `createPointerEvents` casts the ray through the layer's inverse transform when it isn't the identity, so the 3D picks where it is drawn.
- `RenderTexture2D` is a component, as drei's `RenderTexture`: `useRenderTarget`, a portal scene of 2D drawn into the target in a `useFrame` (`frames`, `invalidate`), and a `<primitive>` of the target's texture attached to the parent, `map` by default.

Their events sort where they are drawn. A `<View3D>`'s screen layer is one entry in the parent screen layer's hit order (its `hitArea` is the view's rect). Its portal's `events.compute` (`computeEmbedded` in `packages/core/src/stage/hitTest.ts`) finds the pointer in the view, sets the portal's raycaster from its camera, and gives the raycaster the draw order of that entry (`setLayerOrder` in `packages/core/src/events/hitOrder.ts`), which every hit in the portal starts with. Its 2D and 3D hits sort among themselves as on a root, and before the nested screen layer's own hit, as the container holding it, so the view's handlers and the 2D around it get an event after what is inside, as r3f bubbles from child to parent. A view's backdrops take no events. `<RenderTexture2D>`'s compute is drei's: the parent's raycaster hits the object, the hit's `uv` is the portal's pointer, and the portal's hits start with the draw order of that 3D hit, so they sort just before it. A nested screen layer is hit tested in global coordinates: `hitTestScreen` turns the portal's pointer through the screen layer's world transform.

**Loading.** `useTexture` returns three's `Texture`, which extends pixi's, so a sprite takes it as is. `AssetsLoader` (`packages/2d/src/AssetsLoader.ts`) is pixi's `Assets.load` in three's loader shape, for `useLoader`; `useAsset` is `useLoader(AssetsLoader, url)` typed.

## The entries and their types

Each package's entries are files of its `src` that its `package.json`, its `tsdown.config.ts`, `tsconfig.base.json` and the Vite aliases name:

- `@react-fiber/core`, `packages/core/src/index.tsx`, mirrors the export list of r3f v10's `index.tsx`, which is everything `core/index.tsx` exports plus the entry's own `Canvas`, `createRoot`, `events`, `ThreeElements`, the build flags and the `ReactThreeFiber` namespace. Each value is r3f's own function, re-declared with a type from `packages/core/src/types`, which names pixi-3d, pixi.js or a registered class (`Registered<K>`). Nothing is `export *`'d from the fork, so the declaration bundle never names three, and modules like Environment never enter the bundle. It adds the pixi side: `PixiRenderer`, `useRenderTarget` (our own, since r3f's never disposes its target), `presetsObj`, the bridges, the 2D types and `Register`.
- `@react-fiber/core/extension`, `packages/core/src/extension.ts`: the registry (`FiberExtensionType`, `ObjectHooks`, `SupportParts`), the stage (`addToScene`, `addInElementOrder`, `hitTestScreen`, ...), hit order (`drawOrder`, `setHitOrder`, the bands), and the renderer parts a 3D package extends (camera matrices, backdrops, `program`, `markMaterialTexture`).
- `@react-fiber/2d`, `packages/2d/src/index.ts`: `useAsset` and `AssetsLoader`; importing it registers the 2D elements.
- `@react-fiber/3d`, `packages/3d/src/index.ts`: `objects3D`.
- `@react-fiber/threejs-compat`, `packages/threejs-compat/src/index.ts`, is r3f's API for an r3f app that swaps `@react-three/fiber`: it re-exports core whole and adds `Environment`, `useEnvironment` and `useTextures` (our own implementations of r3f's, which reach three's loaders), `ThreeRenderer`, `catalog` and the compat member types. It augments `Register` with three's classes and `ThreeElements` with the catalog's elements, and importing it installs the package (`install.ts`).
- `@react-fiber/threejs-compat/three`, `packages/threejs-compat/src/three.ts`, is what an r3f app imports from `three`; importing it installs the package too: it re-exports every area module with `export *`. An app can alias `three` to it.
- `@react-fiber/threejs-compat/addons`, `packages/threejs-compat/src/addons/index.ts`, is what an r3f app imports from `three/addons`, re-exporting `packages/threejs-compat/src/addons/loaders`, `packages/threejs-compat/src/addons/controls` (`OrbitControls`, `MapControls`) and `packages/threejs-compat/src/addons/environment` (`HDRLoader`, `RGBELoader`). `GLTFLoader` parses a file with pixi-3d (`glbToGltf`, `normalizeMeshopt`, `loadImages` on a pixi `Loader` of its own, `parseGltf`) and builds three's `GLTF` from the catalog's classes, reading the node, skin and animation data pixi-3d parsed (`Scene3DSource._descriptor`, `source.animations`) and the file's JSON for names and `extras`. Joints become `Bone` nodes that pixi-3d's skeletons follow through `Skeleton.bindContainerBone`, so three's `AnimationMixer` moves them as nodes.

`npm run test:bundle` checks the built files of core, 2d, 3d and threejs-compat for three and r3f's fork, and type-checks an app against their declarations.

## How a frame flows

1. `<Canvas>` measures its container and calls `createRoot(canvas).configure(props)`. The first configure loads the support (`loadPixiSupport`, which runs each registered package's `install`: three's `Object3D` surface, 2d's frame jobs), registers the catalog as `getThree()`, constructs the registered renderer (`ThreeRenderer`) with `{ canvas, antialias }` plus the `renderer` prop, sizes it and awaits `init()`. Core then creates the default `Raycaster`, camera (`PerspectiveCamera(50, 0, 0.1, 1000)` at z = 5, looking at the origin) and `Scene` from the catalog, adds the camera to the scene, sets ACES tone mapping and applies `shadows`.
2. `root.render(children)` mounts the tree with r3f's reconciler. Each element resolves to a catalog class, is constructed with `args`, gets its props through core's `applyProps`, and joins its parent through the support's `add` hook, before its sibling when inserted. Geometries and materials attach to the parent's `geometry` or `material` (`defaultAttach`). A 2D element directly in the canvas joins the scene's screen layer.
3. Every frame, `@pmndrs/scheduler` runs the root's jobs: deferred pointer raycasts, `useFrame` callbacks by phase, then the frustum job (`updateFrustum`, reading the camera's fresh matrices) and the visibility job (`Frustum.intersectsObject` for `onFramed` and `onVisible`), then the render job.
4. The render job calls `renderer.render(state.scene, state.camera)`. The facade finds or makes the scene's view (none while the scene has only 2D), puts the scene's screen layer in the stage with the view inside it, points it at the camera (or the proxy), puts a colour background on the canvas's clear colour, places the view on the viewport, swaps three's tone curve and output in, hands pixi-3d the lights' shadow settings and aims directional and spot lights at their targets, applies the fog, draws a texture background or bakes the environment, and calls `pixi.render()` on the view's container, into the canvas or the current render target. The lights' own settings are put back once it has drawn. pixi-3d's `View3D` runs its transform pass and draws.
5. A pointer event on the canvas reaches core's event layer (through `packages/core/src/events/pointerEvents.ts`), which sets `state.pointer`, calls `raycaster.setFromCamera(pointer, camera)`, and asks the support's `hitTest` for the hits on each object that has a handler: the raycaster's on a 3D node, the screen layer's on a 2D element. `compareHits` sorts them by draw order, 2D over the 3D first and 2D behind it last; core bubbles them up the tree and hands them to the handlers as `ThreeEvent`s.
6. Unmounting removes each element through the `remove` hook and frees it through `dispose` (`destroy` for nodes, geometries and materials). Unmounting the root releases the renderer, whose `dispose()` frees every view and the pixi.js renderer.

## Measuring parity against three

Scenes, examples and docs import the packages only as `@react-fiber/threejs-compat`, `@react-fiber/threejs-compat/three` and `@react-fiber/threejs-compat/addons`, or, in 2D and mixed scenes, `@react-fiber/core` and `@react-fiber/2d`. `tsconfig.base.json` and the Vite aliases resolve those names to the packages' sources. Pointing the first three at `packages/r3f/src/legacy.tsx`, `three` and `tests/harness/three-addons.ts` instead renders the same scene file through r3f's own WebGL entry and real three.js. That is how parity is measured.

Two rules follow:

- A parity scene uses only names both sides export: r3f's API (`Canvas`, `useFrame`, `useThree`, ...), JSX elements, and the classes `@react-fiber/threejs-compat/three` shares with `three`. `PixiRenderer`, the catalog, pixi-3d's own names and the 2D elements are the packages' only. A 2D or mixed scene has nothing to measure against: it lives in a 2D folder (`tests/scenes/2d`, `tests/scenes/mixed`, `examples/2d`), which the three.js side doesn't load, and is held to its own WebGL and WebGPU references.
- One renderer per page. Core keeps the registered namespace (`getThree()`) in a module variable, and the `extend()` registry and React context on `globalThis` under `Symbol.for` keys, so a pixi root and a three root in the same page would share them. Render each side in its own page or iframe: the harness runs the three.js pictures in a vitest project of their own and the playground builds each renderer in its own frame, both reading the two targets from `FIBER_TARGETS` in `scripts/test/aliases.mts` (`tests/README.md`).

## Upstream asks

None of these block us; with the renderer hooks of `packages/r3f/README.md`, which also open the `kind` union and route `insertBefore` through the support's `add`, they would let the library run on published `@react-three/fiber` instead of a fork.

- A `/core` export of `createRoot(canvas, provider)` and `Canvas` with a `provider` prop.
- `Environment` loaded lazily or provided by the support, so `Canvas` doesn't pull three's addons.
- `getThree()` resolved per root from `state.internal.support`, so different renderers can share a page.
- A generic `RootState`, so a support can type it without re-declaring the hooks.
- A click-type event matched to its pointerdown when it has no `pointerId` (Chrome's `dblclick`), so `onDoubleClick` fires; our event layer does it for now.

pixi.js asks, found through the 2D:

- `BlurFilter.destroy` should destroy its two passes. They stay bound to the WebGPU renderer's uniform buffers; 2d's `dispose` hook frees them.
- `Renderer.destroy` frees the uniform batch pipe's buffers and the texture pool before the filter system, whose bind group still holds them, and each one warns `[BindGroup] a '...' was destroyed while still bound to a shader`. `PixiRenderer.dispose` destroys the filter system first. A filter still alive when the renderer goes warns the same way, and r3f disposes elements at idle priority, after a root's renderer is released, so unmounting a root whose tree has filters still logs these warnings on WebGPU.
