# The docs site

The documentation site of react-pixi-fiber, on Docusaurus, as the workspace `@react-fiber/docs` in `packages/docs`. It renders the repo's own sources, a section per package: the guides in `packages/*/src/**/__docs__`, the r3f fork's README and diff, the parity findings in `docs/feasibility.md`, the examples in `examples/` with the pictures the visual tests draw of them, and the JSDoc of every package entry. Nothing is copied by hand. It is built the way [@pixi/layout's site](https://layout.pixijs.io) is, and keeps its design tokens and components.

## Run it

```sh
npm run docs:dev      # dev server on http://127.0.0.1:3000
npm run docs:build    # build into packages/docs/build
npm run docs:serve    # serve that build on http://127.0.0.1:3000
```

Each goes through `packages/docs/scripts/site.mts`, which needs Node 24 and syncs the generated content first. Pass `--name <name>` to give a run its own build and Docusaurus files in `packages/docs/.sites/<name>/`, and `--port <port>` to listen elsewhere, so several builds and servers can run at once; `serve` and `dev` exit with 1 when the port is taken. `serve` answers as GitHub Pages does, through `packages/docs/scripts/pages.mts`, which the crawl and the screenshots use too. That includes its ten-minute cache, so hard-reload a browser you kept open across a rebuild:

```sh
node packages/docs/scripts/site.mts build --name home
node packages/docs/scripts/shoot.mts --name home --out .temp/shots / /docs/
```

`packages/docs/scripts/shoot.mts` screenshots pages at 1440x900 and 390x844, dark and light, and fails on a console error, an exception or a failed request. It serves the build itself, as the crawl does; `--port <port>` points it at a server that is already running, such as the dev server. Look at every picture it takes: a page that loads without an error can still be laid out wrong.

## Check it

`npm run test:site` builds the site as `test` and crawls it with `packages/docs/scripts/crawl.mts`. The crawl serves the build as GitHub Pages does, opens every page of the sitemap and every link it finds from there, the 404 page included, and fails on a console error, an exception, a failed request, or a link to a missing page, file or anchor. It answers requests to other sites itself, with nothing, so another site being slow or down never slows or fails it. It then presses "Run live" on the first example of every topic, and fails when one shows an error, draws nothing in 30 s, or draws a frame of one colour, its background alone. It warns about a page search engines index with no description or canonical URL of its own, and about a layout shift over 0.1, and prints the JavaScript and CSS each page loads, gzipped, and how long each live run took to draw. Crawl your own build with `node packages/docs/scripts/crawl.mts --name <name>`.

Broken links in Markdown and `<Link>` already fail the build. `npm run test:docs`, part of `npm test`, checks the docs against the code (`packages/docs/scripts/typedoc/check.mts`), lints and type-checks `packages/docs`, and runs the unit tests of `docs/plugins/`, `docs/scripts/typedoc/` and `docs/scripts/generators/`. `npm run test:lint` and `npm run test:types` leave `packages/docs` to it. The site's type check reads the packages through their `dist`, so run `npm run build` first. The check fails on:

- a public name of the repo's own code without JSDoc, in any package entry `ENTRIES` lists. What r3f's forked core declares is r3f's, and isn't checked: a file is vendored when a folder on its path is named `r3f`, `vendor` or `vendored` (`isVendored` in `packages/docs/scripts/typedoc/entries.mts`);
- a code block that names a source with `<!-- snippet: examples/<topic>/<name>.example.tsx#region -->` and differs from it (`node packages/docs/scripts/typedoc/snippets.mts --write` brings them up to date);
- a guide `GUIDES` lists that is missing, or a guide file it doesn't list;
- parity findings in `docs/feasibility.md` that the Differences page can no longer read.

## Ship it

Nothing deploys the site yet. A build is static files in `packages/docs/build`, served from `/` with trailing slashes, which suits GitHub Pages; `packages/docs/links/index.ts` holds the address it is built for, `https://react-pixi-fiber.pixijs.io`, which the canonical URLs, the sitemap and `llms.txt` use.

Besides the pages, the build has what search engines and language models read: `sitemap.xml` and `robots.txt`, a canonical URL and social card tags on every page, and `llms.txt`, `llms-full.txt` and the Markdown of every docs page beside it (`/docs/threejs-compat/basic-animations/` has `/docs/threejs-compat/basic-animations.md`). A generator writes that Markdown with the page, from the same tree, into `llms/`, and `plugins/llms` puts each file at its URL and lists them.

## Where things are

- `content/` holds the pages of the docs plugin, served from `/`: `content/docs`, `content/examples` and `content/api`, one sidebar each in `sidebars.ts`.
- `scripts/generators/` has a generator per area, listed in `scripts/sync.mts`. Each returns the files of the folders it owns, and the sync writes them, removes what's stale and keeps those folders out of git. What two generators read, such as the API model or the pages of the Docs section, is built once per sync through `shared`. A page is a Markdown tree (`markdown.mts`): the repo's Markdown parsed once, beside the site's components, which `components.mts` lists with their props, their imports and how each reads as plain Markdown. What is slow to build, the live runtime and the example pictures, is kept in `node_modules/.cache/react-pixi-fiber-docs` by a hash of its inputs (`cache.mts`) and built again only when one changes. `DOCS_ROOT` points every generator at another root, which is how their tests run them on a fixture.
- The guides are Markdown that lives with the code, `packages/<package>/src/**/__docs__/<id>.md`, listed in order in `GUIDES` (`scripts/typedoc/guides.mts`), each in the section of the sidebar of the package that holds it: Getting started (the introduction and installation, in core), Core (Canvas and roots, the stage, events across 2D and 3D, the frame loop, the bridges), 2D, 3D, three.js compat (react-three-fiber's own guides, led by Swap your three.js imports) and The r3f fork. The r3f fork's guide is the fork's own `packages/r3f/README.md`, since it lives outside the diff, followed by a page the content generator writes from `packages/r3f/fork.diff` (`FORK_DIFF` in `content/sidebar.mts`), to which a link to `fork.diff` goes. Each package's section ends with its API reference, and the navbar's 2D, 3D and three.js compat items open their overviews. `scripts/generators/content.mts` writes a page for each at `/docs/<section>/<id>/`, the introduction at `/docs/`, and an overview per section; `content/sidebar.mts` says which pages there are, and `content/mdx.mts` wires a guide into the site: links to other guides, the first mention of a public name in each section linked to its API page, GitHub alerts as admonitions, and a snippet followed by its example's picture as a live `<Example>`. A guide's `npm install` block becomes a tab per package manager.
- The Differences page is `packages/threejs-compat/src/__docs__/differences.md` followed by the parity findings of `docs/feasibility.md`, which `scripts/generators/content/parity.mts` reads: the levels of the verdict (section 1), every row of the parity matrix with its class (section 4), and the major blockers (section 5). Edit the findings and the page follows.
- `scripts/generators/examples.mts` writes the Examples section from `examples/<topic>/<name>.example.ts(x)`, zero or more of them: the gallery at `/examples/` (filters in its query: `?topic=<topic>`, `?q=text`) and a page per example at `/examples/<topic>/<name>/`. The packages' topics come first, `core`, `2d` and `3d` as the navbar orders them (`PACKAGE_TOPICS` in `plugins/example/catalogue.mts`), and `sidebars.ts` puts every other topic, react-three-fiber's guides on threejs-compat, under a three.js compat heading. A topic named like a guide takes its title and links it. An example's title is the `title` string of its `example` object, else the heading of the guide section that first shows its code, else its file name in words; its description is the prose of a guide that brings it in (not the repository's README), else the object's `description`, else the JSDoc above `export const example`. Its picture is the visual harness's reference image, `tests/snapshots/docs/<topic>/<name>.webgl.png`, which it writes to `static/example-pictures` and, cropped to what it draws, to `static/example-thumbs`, as lossless WebP, with the PNG beside it for the card a shared link shows. An example with no picture yet gets a placeholder card. `src/components/Examples` draws the gallery and the parts of an example page.
- `src/components/Example` is the `<Example>` of every MDX page, with `plugins/example` giving it the example's code, picture and program. It runs live on the parts in `src/components/Live`, with the runtime that `scripts/generators/live.mts` builds into `static/runtime`: ES modules of every `@react-fiber/*` entry (from its source, in one build, so the packages share core), @pixi/3d, pixi.js, React and React DOM. A run is a sandboxed iframe that imports the example and mounts it with `src/components/Live/frame/mount.tsx`: the `example.render()` inside a `<Canvas>`, or the `<Canvas>` it returns, asking pixi for the reader's renderer through the `renderer` prop. The frame imports core and 2d; threejs-compat loads only when the example imports it, so the examples of 2d, 3d and core run without it, as their apps would. That mount and the visual harness must agree on what an example exports; change both together. Editing an example in the page is the next seam: layout's site does it with Monaco, and `ExampleSource.program` and `focus` are what an editor shows.
- `scripts/generators/api.mts` writes the API reference from the JSDoc of each entry `ENTRIES` lists in `scripts/typedoc/entries.mts`, by package: `core` (`@react-fiber/core`), `2d`, `threejs-compat`, `three` and `addons` (its `/three` and `/addons`), `3d` and `extension` (`@react-fiber/core/extension`). `scripts/typedoc/api.mts` reads each with oxc, following `export *`, relative imports and the root `tsconfig.json`'s paths into the repo's own files; a path into `.repos` or `node_modules` names another package and isn't followed, and nor is another entry's name, whose pages are its own (threejs-compat's `export * from '@react-fiber/core'` leaves core's names on core's pages). `src/components/Api` draws its signatures, with each name linked to its page, and its fields. A name from r3f's vendored core is marked "From react-three-fiber" and links r3f's docs. Its routes are stable, so other pages link to them, and `apiLinks` in `scripts/generators/api/model.mts` maps every name to its route:
  - `/api/<entry>/`, the entry's overview: `/api/core/`;
  - `/api/<entry>/<kind>/<Name>/`, where `<kind>` is `functions`, `classes`, `constants`, `enums`, `interfaces` or `types`. A const counts as a function when its type is a function, or names a type alias or an interface with a call signature (`useFrame: UseFrame`), and its page shows that call signature: `/api/core/functions/useFrame/`. A module the entry imports with `import type * as` and exports, as `ReactThreeFiber` is, counts as a type: its JSDoc is the block directly above the module's first line, and its members are the types the module exports;
  - `#<member>`, a member by its name as written.

  A page's "Used in" lists the sections of the Docs pages that link it, read from the pages the content generator builds, and the examples that import it.

- `src/pages/index.tsx` is the home page, with its parts in `src/components/Home`. Its packages section (`Home/Features`) is a card per package with links into its section, `Home/Layers` stacks the packages as they fit, and its 2D and 3D section (`Home/TwoD`) is a card per 2D feature and bridge, each with the picture of an example in `examples/2d` or `examples/core` (`/example-pictures/<topic>/<name>.webp`, which the examples generator writes) and a link to its guide section; rename an example or a heading of `mixing-2d-and-3d.md` and update it there. The hero's pictures, `static/img/hero-pixi.png` and `hero-three.png`, are the scene it shows rendered once by pixi-3d through react-pixi-fiber and once by three.js, by the visual harness: a scratch scene with the hero's JSX at 960 by 720 (run with a viewport that fits it), its `webgl` and `three` captures put on the hero's `#111111`. Render them again when either renderer's picture of it changes.
- `src/css/tokens.css` has the design tokens, and `src/css/custom.css` maps them onto Infima.
- Search is `@easyops-cn/docusaurus-search-local`, set up in `docusaurus.config.ts` to index headings and prose but not code or the example pages. `src/theme/SearchBar` and `src/theme/SearchPage` are ejected: the site's own box, which keeps focus where the reader puts it, and its own page, with places to start before anything is typed. Both import the plugin's worker, result rows and CSS by file path (typed in `src/search-plugin.d.ts`), so the plugin is pinned to an exact version in `package.json`: on an upgrade, check both against the plugin's own SearchBar and SearchPage.
